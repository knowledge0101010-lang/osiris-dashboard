# Claude Science

A workbench discipline for computational science: **no result exists without its provenance**.
Every figure, table, and quoted number is welded to the exact code, inputs, environment, and
retrieval that produced it, so it can be reproduced, audited, or forked months later.

## The four rules

1. **Persistent session, not one-shot scripts.** Load data once into a long-lived kernel and
   iterate against it. Re-running a 40-minute import to change an axis label is a bug.
2. **Every artifact gets a manifest.** A figure, table, or model checkpoint written without a
   provenance record is not a result — it's a screenshot.
3. **Every number in prose is a recorded value.** If you write "expression rose 2.4×", that
   `2.4` came from a specific line of code and is stored as such, not retyped from a scroll-back.
4. **Review before delivery.** Run the reviewer over any manuscript, report, or summary. It
   fails loudly on drifted figures, untraceable numbers, and malformed citations.

## Layout

Work inside a project directory. The skill keeps its state in `.science/`:

```
.science/
  kernels/<name>/       live kernel socket, pid, log
  provenance/           artifact manifests (also written as <artifact>.prov.json sidecars)
  values.json           recorded scalar values quotable in prose
  ledger.jsonl          append-only record of every artifact write
  cache/                cached database responses (hashed by request)
```

`scripts/` in this skill directory holds four tools. They are stdlib-only Python 3.9+ — no
install step. Invoke them with the absolute path to this skill's `scripts/` directory.

## 1. Persistent kernels — `kernel.py`

```bash
kernel.py start --name main --lang python     # or --lang r
kernel.py exec  --name main --code 'import scanpy as sc; adata = sc.read_h5ad("data.h5ad"); adata'
kernel.py exec  --name main -f step2.py       # or  -  to read stdin
kernel.py interrupt --name main               # SIGINT into a runaway cell
kernel.py list ; kernel.py status --name main ; kernel.py stop --name main
```

Variables, dataframes, and loaded models stay in memory between calls. Use one kernel per
analysis thread (`--name qc`, `--name de`) rather than one giant namespace. `exec` prints
stdout, stderr, and the value of a trailing expression, and exits non-zero on an exception.

Kernels are per-directory: start them in the project root so relative paths stay stable.

## 2. Provenance — `provenance.py`

Immediately after writing a figure or table:

```bash
provenance.py record --artifact figures/fig2_umap.png \
  --code steps/02_cluster.py \
  --input data/raw_counts.h5ad --input data/sample_sheet.csv \
  --title "UMAP coloured by Leiden cluster" \
  --kernel main
```

This hashes the artifact, the code, and every input; captures the interpreter, platform,
installed packages, and git commit (flagging a dirty tree); and writes both a sidecar
`figures/fig2_umap.png.prov.json` and a ledger entry.

Record any number you intend to quote:

```bash
provenance.py value --key de_genes_fdr05 --value 1284 --code steps/03_de.py \
  --note "Wilcoxon, BH-adjusted FDR < 0.05"
```

Audit at any time — `check` re-hashes and reports `OK` / `DRIFT` / `MISSING`, exiting
non-zero if anything moved:

```bash
provenance.py check           # everything in the ledger
provenance.py show figures/fig2_umap.png
provenance.py ls
```

**Drift is the failure mode this exists to catch**: a figure regenerated by hand, an input
silently overwritten, code edited after the fact. Re-record after every legitimate rerun.

Details and the manifest schema: `references/provenance.md`.

## 3. Scientific databases — `dbfetch.py`

One CLI over the open REST APIs, with on-disk caching so a rerun is byte-identical and the
retrieval itself is provenance-tracked.

```bash
dbfetch.py list                                        # every database and operation
dbfetch.py uniprot get P04637
dbfetch.py uniprot search 'gene:TP53 AND organism_id:9606' --limit 5
dbfetch.py alphafold get P04637 --out structures/
dbfetch.py pdb search TP53 --limit 10
dbfetch.py ncbi search pubmed 'single-cell CRISPR screen' --limit 20
dbfetch.py ensembl lookup ENSG00000141510
dbfetch.py chembl search imatinib
dbfetch.py pubchem get aspirin --by name
dbfetch.py opentargets associations ENSG00000141510 --limit 10
```

Add `--out FILE`, `--format tsv|json|raw`, `--no-cache`, `--quiet`. Responses land in
`.science/cache/` keyed by the full request URL, and every fetch appends to the ledger, so a
downstream figure can point back to the exact record that fed it.

Full endpoint table, per-database operations, rate limits, and how to add a database:
`references/databases.md`.

## 4. The reviewer — `review.py`

Run before anything leaves the project:

```bash
review.py --manuscript draft.md
review.py --manuscript draft.md --bib refs.bib --online   # resolve DOIs/PMIDs
```

It flags, with severities:

- **figure-missing / figure-drift / figure-unprovenanced** — a referenced figure that is gone,
  whose bytes no longer match its manifest, or that never had one.
- **number-untraceable** — a numeric claim in prose that matches no recorded value and no
  value in a results table.
- **citation-malformed / citation-unresolved / citation-missing-bib** — DOIs and PMIDs that
  are ill-formed, absent from the bibliography, or (with `--online`) that don't resolve.
- **artifact-orphan** — a file in the results tree with no manifest.

Blockers exit non-zero. Fix or explicitly justify each one; do not deliver over a red review.
Checks and tuning: `references/review.md`.

## Compute

Local kernels cover most work. For anything that needs a cluster or a GPU, see
`references/compute.md` — it covers SLURM over SSH (`sbatch` generation, job polling,
result retrieval), Modal, and the rule that job scripts are themselves provenance-recorded
inputs, not throwaway text.

## Domain playbooks

`references/domains.md` holds the working recipes and standard pitfalls for:
single-cell RNA-seq · bulk RNA-seq and genomics · proteomics · structural biology ·
cheminformatics · phylogenetics.

Read the relevant section before designing an analysis — each one lists the conventional
tool chain, the checks that catch the usual silent failures (ambient RNA, batch confounding,
multiple-testing, alignment gaps, tautomer handling, long-branch attraction), and which
databases to reach for.

## Working rhythm

1. State the question and the analysis plan in one short paragraph before running anything.
2. Start a kernel; load and **describe** the data (shape, dtypes, missingness, batch structure)
   before transforming it.
3. Iterate in the kernel. Write each settled step to a numbered file in `steps/` so the
   analysis is replayable end to end.
4. On every figure/table: `provenance.py record`. On every quotable number:
   `provenance.py value`.
5. Draft alongside the analysis in Markdown/LaTeX, quoting only recorded values.
6. `provenance.py check` then `review.py` before delivery. Report what the reviewer said.

## Honest reporting

Say what the data supports and nothing more. A result that failed, a batch effect you could
not remove, an underpowered comparison, a database record with a mismatched sequence — state
it plainly in the write-up. Negative and ambiguous results are results; laundering them is
the one unrecoverable error in this workflow.
