## §0 · 하네스 명제 — 에이전시는 어디서 오는가

> **모델은 무엇을 할지 정한다. 하네스는 툴·상태·한계를 준다.**

### 문제

모델 호출 하나는 **입력 하나에 응답 하나**다. 행동하기로 *결정*할 수는 있지만
스스로 행동할 수는 없다. 지속 상태도, 툴 실행기도, 파일 접근도, 권한 게이트도 없다.

### 하네스가 해야 하는 4가지

1. **행동이 실행될 장소를 준다.**
2. **모델에게 쓸모 있는 관측을 준다.**
3. **부작용이 세상에 닿기 전에 게이팅한다.**
4. **상태를 지속시켜 나중 호출이 앞 호출 위에 쌓이게 한다.**

이 네 가지가 없으면 모델은 답변만 할 수 있다. 툴을 돌리거나, 결과를 관측하거나,
호출 간에 작업을 기억할 수 없다.

### 소유권 분리

| 모델이 소유 | 하네스가 소유 |
| --- | --- |
| 판단 | 루프 |
| 툴 선택 | 툴 실행과 라우팅 |
| 언제 멈출지 | 권한, 훅 |
| | 지식 로딩, 태스크, 코디네이션 |

Claude Code에서 **대부분의 코드는 모델 호출 바깥에 있다.** 반면 `mini-swe-agent`는
에이전트 클래스 전체가 약 150줄이고, bash 툴 하나로 모든 걸 처리한다.
두 극단을 나란히 보면 하네스가 무엇을 사는지가 선명해진다.

### 하네스는 많을수록 좋은 게 아니다 ⚠️

모든 레이어는 **지금 모델이 혼자 못 하는 것**을 메운다. 따라서 모든 레이어에 두 가지 비용이 붙는다.

1. 유지보수할 코드가 늘고, 버그가 살 자리가 늘어난다.
2. **한 세대의 모델에 묶인 설계가 된다.** 새 모델이 스스로 계획하고 복구하고 검증한다면,
   옛 우회로를 강제하는 건 성능을 *떨어뜨린다*.

> 그래서 하네스 엔지니어링은 더하기만이 아니다.
> **모델이 바뀌면 각 레이어를 재평가하라 — 여전히 도움 되는 건 남기고, 새 모델이 커버하는 건 지워라.**

이걸 측정 가능하게 만드는 게 §20(관측)과 §21(루프 엔지니어링)이다.

### 어디서 에이전트가 먼저 작동하는가

작업이 에이전트에 적합한지는 두 가지가 결정한다.

1. **목표를 얼마나 정확히 진술할 수 있는가**
2. **결과를 기계가 검사할 수 있는가**

코딩은 둘 다 높다. 티켓이나 실패하는 테스트가 목표를 진술하고,
테스트·타입·린터·git이 언제 끝났는지 말해준다. 사람이 자기 편의를 위해 만들어 둔 인프라를
에이전트가 **기성품 검증 하네스**로 재활용한다. 코딩 에이전트가 먼저 성숙한 이유다.

한쪽이 없으면 애매하게 어려워지는 게 아니라 **특정한 방식으로 실패한다**.

| 상황 | 실패 양상 | 처방 |
| --- | --- | --- |
| 목표는 명확, 자동 검사 없음 | 루프에 정지 조건이 없어, *아무도 아니라고 안 하니까* 다 됐다고 선언 | §21에서 검사를 만든다 |
| 자동 검사는 있음, 목표가 불명확 | 루프가 목표 대신 검사를 겨냥. "아무것도 안 깨졌음"을 증명하는데 그건 시킨 게 아님 | 검사로는 못 고침 — 목표를 다시 써라 |

### 실패 모드

- **하네스 동작을 모델의 공로로 돌리기.** 권한 체크와 에러 복구는 하네스 동작이다. 실패하면 하네스를 고쳐라.
- **모델이 해야 할 결정을 하드코딩.** 경직된 툴 순서와 스크립트화된 계획은 모델과 싸운다.
- **하네스가 너무 적음.** 툴·권한·컨텍스트 관리 없는 루프는 모델을 챗봇 수준에 묶는다.
- **하네스가 너무 많음.** 옛 모델용으로 만든 레이어가 새 모델의 발목을 잡는다.
- **모델 정책을 하네스 설정으로 착각.** 예: "코드를 언제 그만 읽고 편집을 시작할지"는
  학습된 정책이다. 프롬프트 한 줄이나 스텝 제한은 이를 *밀어줄* 뿐, *정하지* 못한다.

## §1 · 에이전트 루프 — 어떻게 계속 도는가

> **하나의 루프가 모델이 답하거나 툴을 요청할 때까지 계속 모델을 호출한다.**

### 두 개의 루프, 하나의 `messages[]`

채팅창을 떠올려보자. "타이베이 날씨 어때? 우산 가져가야 해?"라고 물으면
모델은 날씨 툴을 부르고, 결과를 본 뒤 강수확률 툴을 부르고, 그제서야 답한다.

**즉 한 턴 안에서 모델은 여러 번 호출된다.** 질문부터 최종 답변까지가 **내부 루프**(inner loop) —
한 유저 턴이다. 그 다음 "내일은?"이라고 물으면 새 턴이고, **외부 루프**(outer loop)가
턴을 이어 붙여 하나의 대화로 만든다.

```python
def run_turn(messages, model, max_steps=10):        # 내부 루프: 공유 messages[] 위의 한 턴
    for _ in range(max_steps):                       # 폭주 방지 백스톱
        response = model(messages)                   # Messages API 호출 1회
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason != "tool_use":       # 이 턴의 답이 나옴
            return final_text(response)

        results = []                                 # tool_use: 각각 실행 후 되먹임
        for block in response.content:
            if block.type == "tool_use":
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": run_tool(block.name, block.input)})
        messages.append({"role": "user", "content": results})

    raise RuntimeError("hit max_steps without end_turn")
```

```python
messages = []                                        # 외부 루프: 대화 전체는 호출자가 소유
for user_text in turns:
    messages.append({"role": "user", "content": user_text})
    reply = run_turn(messages, model)                # 제자리 append — 턴 N은 턴 1..N-1을 본다
```

> ⚠️ **이건 교육용 최소 루프다. 그대로 쓰면 안 된다.** 일부러 빠져 있는 것:
>
> - **권한 게이트.** `run_tool` 앞에 `allow`/`ask`/`deny` 판정이 없다 — §3이 넣는다.
> - **툴 실패 처리.** `run_tool`이 예외를 던지면 `tool_result`가 안 붙어 트랜스크립트가 깨진다.
>   실제 코드는 잡아서 `is_error: True`로 돌려줘야 한다
>   ([§11](03-layer3-knowledge-resilience.md#11--에러-복구--긴-작업이-실패를-어떻게-견디는가)).
> - **`stop_reason` 분기.** 아래 참조.
>
> 각 결함은 뒤 섹션이 하나씩 메운다. 그게 이 학습 구조의 방식이다.

### 루프를 굴리는 `stop_reason`

위 스니펫은 `!= "tool_use"`를 전부 최종 답으로 취급한다. **실제 API는 그렇지 않다.**

| 값 | 의미 | 올바른 처리 |
| --- | --- | --- |
| `tool_use` | 툴 호출을 생성했다 | 실행 → 결과 append → 다시 호출 |
| `end_turn` | 자연스럽게 응답을 마쳤다 | **여기서만** 최종 답으로 반환 |
| `pause_turn` | 반복 한도에 걸려 일시정지 | 어시스턴트 메시지를 **그대로 되돌려 보내** 계속시킨다 |
| `max_tokens` | `max_tokens`에 잘렸다 | 잘린 응답이다. 이어받거나 한도를 올린다 |
| `stop_sequence` | 지정한 정지 시퀀스를 만났다 | `stop_sequence` 필드에 어느 것인지 담긴다 |
| `refusal` | 안전 분류기가 생성을 거절 | 재시도해도 같다. 로깅하고 다르게 접근한다 |

`pause_turn`을 최종 답으로 처리하면 작업이 조용히 중간에 끊긴다.
`max_tokens`를 최종 답으로 처리하면 잘린 문장을 결과로 쓴다.

`messages[]`가 이 세션의 **전체 대화 메모리**다. 툴 결과도 어시스턴트 답변도 모두 들어간다.

### 시스템별 비교

| | Claude Code | mini-swe-agent |
| --- | --- | --- |
| 루프 구동 | async generator. 모든 툴이 하나의 계약으로 dispatch에 연결 | while 루프. 매 스텝 모델에 명령어를 묻고 실행 |
| 정지 신호 | `stop_reason: end_turn` | `role: "exit"` 메시지. 환경이 submit 마커를 감지 |
| 병렬 툴 | O — 한 턴의 툴 호출을 병렬 실행 | X — 순차 |
| 스트리밍 | O — 토큰·툴 호출·툴 결과를 발생 즉시 방출 | X |

### 실패 모드

- **정지 조건 없음.** 버그나 툴 루프가 무한히 돈다 → max-step 또는 토큰 한도.
- **루프 중간 컨텍스트 오버플로.** `messages[]`는 커지기만 한다 → §8.
- **부분 툴 실패.** 실패해도 **반드시 `tool_result`를 반환해야** 모델이 복구할 수 있다.
- **결과 유실.** 어시스턴트의 tool call이나 tool result 중 하나라도 빠지면 트랜스크립트가 깨진다. **둘 다 append하라.**

## §2 · 툴 런타임 — 어떻게 호출·라우팅되는가

> **능력을 추가한다 = 툴을 등록한다. 루프는 그대로다.**

### 런타임이 해야 하는 것

1. 어떤 툴이 있는지 모델에게 알린다.
2. 각 툴의 입력 스키마를 기술한다.
3. `tool_use`를 이름으로 라우팅한다.
4. 안전한 호출은 가능하면 병렬 실행한다.
5. **큰 툴 카탈로그를 발견 가능한 상태로 유지한다.**

5번이 실무에서 가장 자주 무너진다. MCP 서버를 여러 개 붙이면 툴 정의만으로
컨텍스트가 수천 토큰씩 먹힌다. 그래서 **지연 로딩(deferred tools)** 패턴이 나온다 —
이름만 노출하고, 스키마는 검색 툴로 가져오게 한다.

### 툴 설계는 곧 에이전트 UX

Anthropic의 *Writing Effective Tools for Agents*가 다루는 지점:

| 원칙 | 나쁜 예 | 좋은 예 |
| --- | --- | --- |
| 이름이 명확 | `process` | `read_file` |
| 스키마 최소 | 안 쓰는 optional 필드 10개 | 필요한 3개 |
| 에러가 다음 행동을 알려줌 | `Error: failed` | `Error: file not found at /a/b. Use glob to locate it.` |
| 반환값 일관 | 성공은 문자열, 실패는 null | 항상 같은 shape |
| 툴 하나는 한 가지 개념 | `solve_customer_problem` | `read_order`, `refund_order` |

### MCP 툴 어노테이션 — 위험 어휘

MCP는 네 가지 힌트를 정의한다: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`.
**강제 계약이 아니라 하네스의 권한 결정에 들어가는 입력값**이다.

여기서 나오는 개념이 **치명적 3요소(lethal trifecta)**:

```text
비공개 데이터 접근  +  신뢰 불가 콘텐츠 노출  +  외부 통신
= 개별 툴은 안전해도 조합이 위험
```

단일 툴 안전성 분석이 놓치는 게 정확히 이 지점이다.

## §3 · 권한 & 샌드박스 — 부작용을 어떻게 게이팅하는가

> **각 행동을 시스템에 닿기 전에 검사한다.**

1. 실행 전에 각 툴 호출을 검사한다.
2. `allow` / `ask` / `deny`를 결정한다.
3. 미리 승인되지 않은 위험한 호출은 사람에게 묻는다.
4. 실행되더라도 피해를 제한한다 (샌드박스).

### 게이트의 위치

```text
model ──▶ tool_use ──▶ [권한 게이트] ──▶ 툴 실행 ──▶ tool_result ──▶ model
                            │
                            └─▶ ask ──▶ 사람
                            └─▶ deny ──▶ 거부 사유를 tool_result로 반환
```

**핵심:** 거부도 `tool_result`로 돌아가야 한다. 거부 사유를 읽고 다른 방법을 찾는 것이
평가 대상 행동이다. (§23의 "거부된 호출도 로그에 남긴다"와 연결)

### 프롬프트로 권한을 대신하지 마라

Anthropic *Beyond Permission Prompts*의 요지: 자연어 권한 문구에 의존하는 대신
**구조화된 권한/인가 시스템**을 하네스에 넣어라.
모델에게 "제발 멈춰줘"라고 부탁하는 건 힌트지 정지 조건이 아니다.

Deep Agents 문서의 표현도 같다:

> "에이전트는 툴이 허용하는 건 뭐든 할 수 있다.
> 경계는 **툴/샌드박스 레벨에서 강제**하라. 모델의 자기 규율을 기대하지 마라."

## §4 · 훅 — 확장은 루프에 어떻게 붙는가

> **훅은 루프 주변의 고정된 지점에 동작을 덧붙인다.**

### 왜 훅인가

프롬프트로 규칙을 넣으면 **모델이 무시할 수 있다.** 훅은 하네스 코드가 실행하므로
무시할 수 없다. "커밋 전엔 항상 lint를 돌려라"는 프롬프트 문장이 아니라
`PreToolUse` 훅이어야 한다.

### 대표 라이프사이클 이벤트

| 이벤트 | 시점 | 전형적 용도 |
| --- | --- | --- |
| `SessionStart` | 세션 시작 | 의존성 설치, 환경 점검, 컨텍스트 주입 |
| `PreToolUse` | 툴 실행 직전 | 차단, 인자 검증, 감사 로그 |
| `PostToolUse` | 툴 실행 직후 | 포맷터 실행, 결과 후처리 |
| `Stop` / `SessionEnd` | 종료 | 정리, 알림, 리포트 |

Claude Code는 27종의 이벤트를 가진 훅 파이프라인을 갖는 것으로 분석된다.
OpenAI Codex도 같은 이름(`SessionStart`, `PreToolUse`, `PostToolUse`)의 훅 프레임워크를 제공한다 —
**업계 공통 패턴**이 됐다는 뜻이다.

### 미들웨어라는 다른 표현

LangChain의 `AgentMiddleware`는 6개의 조합 가능한 훅으로 같은 문제를 푼다:

```text
before_agent → before_model → wrap_model_call → wrap_tool_call → after_model → after_agent
```

이걸로 가능한 것: PII 마스킹(프롬프트에 맡길 수 없는 것), 동적 툴 주입,
작업 중 모델 스왑, 재시도/폴백/HITL 인터럽트.
**횡단 관심사를 개별 에이전트에 박아 넣지 않는 참조 설계다.**

### 실패 모드

- **훅이 조용히 실패.** 훅 실패가 무시되면 게이트가 없는 것과 같다. 실패를 시끄럽게 만들어라.
- **훅 안에서 느린 작업.** 매 툴 호출마다 3초씩 걸리면 루프 전체가 죽는다.
- **훅 출력이 컨텍스트를 오염.** 훅 결과는 유저 피드백으로 취급되므로 장황하면 비싸다.

## 이 레이어를 제거할 수 있는 조건

| 레이어 | 존재 이유 | 제거 가능 시점 |
| --- | --- | --- |
| §1 루프 | 모델 호출이 스스로 이어지지 않음 | 서버측 에이전틱 루프가 표준이 되면 (부분적으로 이미 진행 중) |
| §2 지연 툴 검색 | 큰 툴 카탈로그가 컨텍스트를 먹음 | 컨텍스트 비용이 무의미해지거나 서버가 툴 선택을 대신하면 |
| §3 권한 게이트 | **제거 불가** — 모델 능력과 무관한 신뢰 경계 | 해당 없음 |
| §4 훅 | 프롬프트 준수가 확률적임 | 결정론적 강제가 필요한 한 제거 불가 |

§3은 다른 레이어와 성격이 다르다. **권한은 모델이 좋아진다고 없어지지 않는다.**
"모델이 이제 안전하니까 게이트를 빼자"는 카테고리 오류다 —
게이트는 모델의 능력이 아니라 **당신이 감당할 수 있는 피해 범위**에 대한 결정이다.
