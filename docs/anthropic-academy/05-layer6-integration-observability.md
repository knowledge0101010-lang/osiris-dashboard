## §19 · MCP / 플러그인 / 채널 — 세상에 어떻게 닿는가

> **능력이 부족한가? 꽂아라. 하네스는 하나의 표준 프로토콜로 세상에 닿는다.**

### 세 가지 확장 축

| 축 | 무엇이 들어오나 | 예 |
| --- | --- | --- |
| **MCP** | 툴, 리소스, 프롬프트 | GitHub, Figma, Google Drive 서버 |
| **플러그인** | 커맨드, 스킬, 에이전트, 훅 묶음 | 팀이 설치하는 워크플로 패키지 |
| **채널** | 실행을 시작하는 입구 | Slack, GitHub 웹훅, CLI, 웹 |

셋이 합쳐져서 **툴 풀(tool pool)** 을 구성한다.

### MCP의 3요소

MCP 코스에서 배우는 것:

| | 무엇 | 누가 주도 |
| --- | --- | --- |
| **Tools** | 모델이 호출하는 함수 | 모델 |
| **Resources** | 읽을 수 있는 데이터 (URI로 식별) | **호스트 애플리케이션** |
| **Prompts** | 재사용 가능한 프롬프트 템플릿 | 사용자 |

**세 축의 주도권이 다르다는 게 요점이다.** Tools는 모델이 호출을 결정하고,
Prompts는 사용자가 고르고, **Resources는 호스트 애플리케이션이 무엇을 읽어
컨텍스트에 넣을지 정한다.** URI는 데이터를 *식별*할 뿐, 모델에게 아무거나
가져올 권한을 주지 않는다.

**그래서 Resources가 과소평가된다.** 데이터를 툴 호출 결과로 밀어 넣는 대신
URI로 노출해 두면, 호스트가 필요한 시점에 필요한 것만 붙인다 —
§7의 점진적 공개와 같은 원리이고, 결정 주체가 호스트라는 점이 안전 속성이다.

### MCP의 비용

서버를 붙이면 흔히 **그 서버의 툴 스키마 전부가 컨텍스트에 상주한다.**
서버 5개면 툴 정의만 수만 토큰이 될 수 있다.

> ⚠️ 다만 이건 **MCP의 요구사항이 아니라 호스트의 즉시 로딩(eager loading) 선택**이다.
> 클라이언트는 `tools/list`로 카탈로그를 받아 **모델 컨텍스트 밖에** 두고,
> 필요할 때만 전체 스키마를 주입할 수 있다. MCP 클라이언트 모범 사례는 이걸
> **점진적 발견(progressive discovery)** 이라 부르고, 툴 정의가 컨텍스트 윈도우의
> 1–5%를 넘길 때 전환하라고 권한다.

대응책:

1. **지연 로딩 (점진적 발견).** 이름과 설명만 노출하고, 전체 스키마는
   `search_tools` 류의 메타 툴로 필요할 때 가져온다. 조회한 정의는 호스트가 캐시하고,
   `notifications/tools/list_changed`로 갱신한다.
2. **서버를 필요할 때만 활성화.**
3. **툴 출력을 컨텍스트 밖에서 가공.** `context-mode` 같은 접근 —
   대용량 툴 출력(Playwright 스냅샷, 로그)을 샌드박싱하고 관련 조각만 회수한다.

### 프로토콜의 한계 — Codex가 자체 프로토콜을 만든 이유

OpenAI가 Codex 하네스를 노출하며 MCP 대신 Item/Turn/Thread 프로토콜
(JSON-RPC/JSONL over stdio)을 만든 사례가 시사적이다.
**승인 플로, 스트리밍 diff, 스레드 지속**이 MCP의 툴 중심 모델로는 부족했다는 것.

> 교훈: MCP는 **툴 통합**의 표준이지 **하네스 제어 평면**의 표준이 아니다.

### 파일시스템을 프로토콜로 쓰기

반대 방향의 접근도 있다. Mirage 같은 프로젝트는 S3, Slack, Gmail, GitHub, Redis를
**하나의 가상 파일시스템으로 마운트**한다. N개의 API를 배우는 대신
`grep`, `cat`, `cp`를 쓰게 한다.

핵심 통찰은 §9에서 본 것과 같다 — **모델은 이미 셸에 유창하다.**
그 어휘를 쓰면 툴 스키마 비대화가 사라지고, 서비스 간 파이프라인이
셸 스크립트처럼 조합된다.

### 실패 모드

- **서버를 다 켜 둠.** 컨텍스트가 스키마로 채워진다.
- **툴 출력이 거대함.** 한 번의 호출이 윈도우를 절반 먹는다.
- **신뢰 불가 서버.** MCP 서버는 코드를 실행한다. 출처를 검증하라.
- **어노테이션을 강제로 착각.** `readOnlyHint`는 힌트지 보장이 아니다 (§2).

## §20 · 관측성 — 잘 돌아가는지 어떻게 아는가

> **볼 수 없는 건 고칠 수 없고, 아무도 기록하지 않은 실행은 채점할 수 없다.**

### 무엇을 기록하는가

| 층위 | 기록 | 용도 |
| --- | --- | --- |
| **트레이스** | 매 모델 호출, 툴 호출, 결과 | 디버깅, 사후 분석 |
| **메트릭** | 토큰, 지연, 스텝 수, 성공률 | 추세, 회귀 감지 |
| **이벤트** | 권한 거부, 압축 발생, 재시도 | 하네스 동작 감사 |

`orchestra/dispatch.mjs`가 `codex exec --json`의 JSONL을
`.orchestra/runs/<id>/events.jsonl`에 그대로 흘려 넣는 게 트레이스 층이다.
**가공하지 않고 원본을 남기는 것**이 중요하다 — 무엇을 볼지 나중에 정해지기 때문이다.

**그런데 원본 트레이스는 프롬프트, 툴 인자, 툴 결과, 파일 내용, 사용자 식별자를 그대로 담는다.**
그래서 "원본을 남겨라"는 다음 세 가지가 갖춰진 뒤에만 유효한 조언이다.

| 통제 | 최소선 |
| --- | --- |
| **레닥션** | 비밀·자격증명 패턴을 기록 시점에 마스킹. 사후 정리는 이미 늦다 |
| **접근 제한** | 트레이스 디렉터리 권한을 좁히고, 저장소에 커밋하지 않는다 (`.orchestra/`는 gitignore) |
| **보존 기한** | 언제 지울지 정해 둔다. "영구 보관"은 정책이 아니라 정책의 부재다 |

이 셋이 없으면 §20은 디버깅 도구가 아니라 **유출 경로**다.

### 프로세스 메트릭

결과만 보면 놓치는 게 있다.

| 메트릭 | 무엇을 잡나 |
| --- | --- |
| **불법 호출 수** | 없는 툴, 잘못된 인자 → 스키마가 나쁘다는 신호 |
| **스텝 수** | 같은 결과를 몇 턴에 냈는가 |
| **재시도 횟수** | 얼마나 자주 틀렸다가 고쳤는가 |
| **압축 발생** | 컨텍스트 압력이 어디서 오는가 |

**결과가 통과해도 프로세스가 나쁘면 다음엔 실패한다.**

### 하네스 변경이 성능을 좌우한다는 증거

- LangChain: 하네스만 바꿔서 Terminal Bench 2.0에서 30위 → 톱5.
  모델 교체 없음. 구조화된 검증 루프, 컨텍스트 주입(디렉터리 맵 + 시간 예산 경고),
  루프 감지 미들웨어, 계획·검증 단계에 사고를 집중시키는 "reasoning sandwich".
- LangChain: 하네스 튜닝만으로 Nemotron 3 Ultra를 Opus 4.8과 1점 차이까지,
  비용은 약 1/10로 (\$4.48 vs \$43.48).
- Anthropic 2026 Agentic Coding Trends: **인프라 설정만으로 벤치마크가 5%p 이상 움직인다.**
- Anthropic 4월 postmortem: Claude Code 품질 저하의 원인이 세 개의 독립적인
  **하네스 레벨** 변경이었다 — 기본 reasoning effort 하향, 오래된 세션에서
  thinking history를 계속 떨어뜨린 캐싱 버그, 지나치게 공격적인 verbosity 제한 프롬프트.

> 마지막 사례가 이 섹션의 존재 이유를 가장 잘 보여준다.
> **프롬프트 문구, 캐시 헤더, 기본 파라미터 같은 사소해 보이는 하네스 조정이
> 눈에 보이는 회귀로 복리처럼 누적된다.** 그리고 그걸 분리해내려면 트레이스가 필요하다.

### 실패 모드

- **트레이스가 없음.** 회귀가 나도 원인을 못 찾는다.
- **가공된 로그만 남김.** 나중에 필요한 필드가 없다.
- **메트릭이 결과만.** 프로세스 문제를 놓친다.
- **자율 실행에 리포팅이 없음.** 아무도 안 볼 때의 실패가 발견되지 않는다.
- **트레이스에 비밀이 들어감.** 관측성이 유출 경로가 된다.

## §23 · 평가 — 변경이 개선인지 어떻게 아는가

> **합격률은 그 뒤에 있는 환경만큼의 가치를 갖는다.**

### §20과 다른 질문

| | §20 관측성 | §23 평가 |
| --- | --- | --- |
| 질문 | **무슨 일이 있었나** | **그게 좋았나** |
| 대상 | 프로덕션 | 테스트 환경 |
| 산출 | 트레이스, 메트릭 | 점수, 비교 |
| 시점 | 상시 | 변경 시 |

### 왜 에이전트 평가가 어려운가

모델 호출 하나면 쉽다 — 프롬프트 보내고, 정답과 비교하고, 센다.

에이전트는 그 전제를 전부 깬다:

- 여러 턴을 돈다.
- 작업이 명시하지 않은 정보를 **사용자에게 묻는다**.
- 저장된 데이터를 **바꾸는 툴을 호출한다**.
- 같은 결과에 **다른 경로로** 도달한다.
- 같은 빌드의 같은 작업 두 실행이 **서로 다를 수 있다**.

그래서 프롬프트 목록이 아니라 **테스트 베드**가 필요하다.

### 평가 환경의 5요소

4개는 데이터, 1개는 제어 흐름.

| 요소 | 내용 |
| --- | --- |
| **데이터셋** | 태스크 레코드. 시작 상태 + 사용자가 원하는 것 + 검사 방법 |
| **환경 상태** | 시작하고 끝나는 가변 데이터: 주문, 파일, DB. **현실적이면서 리셋 가능해야** |
| **툴** | 에이전트가 쓸 수 있는 연산. **원자적으로** (주문 읽기, 환불하기) — "고객 문제 해결하기" 같은 툴 금지 |
| **루브릭** | 끝난 실행이 점수가 되는 방법 |
| **상호작용 프로토콜** | 누가 언제 말하는가, 에피소드가 언제 끝나는가 |

### 리셋이 없으면 평가가 아니다

```python
def reset(self):
    self.state = deepcopy(self.initial)   # 에피소드마다 새 복사본
    self.calls = []
```

리셋이 없으면 환불 태스크의 두 번째 실행은 **이미 환불된 주문**에서 시작한다.
그 점수는 아무 의미가 없다.

### 거부된 호출도 결과를 반환한다

```python
if tool is None:
    self.calls.append((name, False))       # 불법: 그런 툴 없음
    return f"error: no tool named {name}"  # 이유를 말한다
```

**거부에서 회복하는 것 자체가 평가 대상 행동이다.**
맨 실패 플래그가 아니라 이유를 담은 메시지를 돌려줘야 한다.

### 시뮬레이션된 사용자

대부분의 벤치마크는 첫 메시지에 전체 요청을 준다. **실제 사용자는 안 그런다.**
"주문에 뭔가 문제가 있어요"로 시작하고, 물어보면 나머지를 준다.

그래서 시뮬레이션된 사용자는 스크립트를 쥐고 **턴당 하나의 사실만 푼다**.
이게 **"묻기"를 채점 가능한 능력으로 만든다.**

### 세 갈래 판정

통과/실패 하나는 신호가 얇다. 판정을 세 질문으로 쪼개고 각각 증거를 명시하게 한다.

| 질문 | 증거 |
| --- | --- |
| **결과 (Outcome)** | 실행이 올바른 상태를 남겼는가 — 상태 자체, 코드로 검사 가능한 건 코드로 |
| **과정 (Process)** | 규칙을 따랐는가: 허용된 툴, 필요한 순서, 확인 생략 없음 — 트레이스의 툴 호출 |
| **품질 (Quality)** | 코드 검사로 표현 못 하는 부분이 좋은가 — 루브릭, 실패한 항목을 명시 |

**분리하면 무엇을 고칠지가 나온다.**

- 결과 통과 + 과정 실패 → **운이 좋았다**
- 과정 통과 + 결과 실패 → **규칙이 틀렸다**

### Pass^k

같은 작업을 k번 돌려서 **전부** 통과해야 통과로 치는 지표.
에이전트의 비결정성 때문에 pass@1은 운을 측정한다.
3%p 차이가 샘플링 노이즈인지 실제 개선인지 구분하려면 반복이 필요하다.

### 평가가 하네스 작업의 학습 데이터다

LangChain의 표현이 정확하다:

> **evals are the training data for harness work.**

하네스를 고치는 루프(§21의 개선 루프)는 평가 없이는 돌 수 없다.
무엇이 나아졌는지 모르면 변경이 개선인지 우연인지 알 수 없다.

### 실패 모드

- **환경 리셋 없음.** 두 번째 실행부터 점수가 무의미.
- **데이터셋이 학습에 유출.** 점수가 기억을 측정한다.
- **한 번만 실행.** 노이즈를 개선으로 착각.
- **루브릭이 실행 후에 작성됨.** 결과에 맞춰 기준이 움직인다.
- **툴이 너무 크다.** "문제 해결" 툴 하나면 에이전트를 평가하는 게 아니라 그 툴을 평가하는 것.
- **결과만 채점.** 규칙을 어기고 통과한 실행을 성공으로 기록한다.

## 이 레이어를 제거할 수 있는 조건

| 레이어 | 존재 이유 | 제거 가능 시점 |
| --- | --- | --- |
| §19 MCP | 하네스가 외부 시스템을 모름 | 제거 불가 (통합은 영구 요구사항) |
| §19 지연 툴 로딩 | 스키마가 컨텍스트를 먹음 | 컨텍스트 비용이 무의미해지면 |
| §20 트레이스 | 관측 없이 디버깅 불가 | **제거 불가** |
| §23 평가 환경 | 변경의 효과를 모름 | **제거 불가** |

**§20과 §23은 이 노트에서 "절대 제거 불가" 표시가 붙는 몇 안 되는 레이어다.**
그리고 §0에서 말한 "모델이 바뀌면 각 레이어를 재평가하라"를 실행하려면
이 둘이 먼저 있어야 한다. 관측과 평가가 없으면 **무엇을 지워도 되는지 알 수 없다.**
