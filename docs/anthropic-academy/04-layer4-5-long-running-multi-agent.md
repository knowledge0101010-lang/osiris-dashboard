## §12 · 태스크 시스템 — 작업이 턴을 넘어 어떻게 지속되는가

> **작업을 의존성을 가진 지속적 태스크로 저장한다.**

1. 각 작업 단위를 **지속되는 객체**로 저장한다.
2. **순서를 데이터로** 표현한다.
3. 턴·세션·크래시를 **살아남는다**.
4. **하나의 워커만** 태스크를 점유(claim)할 수 있다.

### 투두(§5)와 무엇이 다른가

| | §5 투두 | §12 태스크 |
| --- | --- | --- |
| 수명 | 한 세션 | 영구 |
| 소유자 | 한 에이전트 | 여러 에이전트가 경쟁 |
| 순서 | 암묵적 (목록 순서) | **명시적 의존성 그래프** |
| 저장 | 인메모리 구조체 | 파일/DB |
| 점유 | 없음 | **락 필요** |

### 의존성은 그래프다

```json
{
  "id": "api",
  "dependsOn": ["schema"],
  "verify": "npm run test -- src/app/api"
}
```

의존성 그래프를 데이터로 두면 두 가지가 공짜로 따라온다.

1. **사이클 검출.** 사이클이 있으면 어떤 태스크도 준비 상태가 되지 않는다 —
   실행 중에 교착으로 발견하지 말고 로드 시점에 거부해야 한다.
2. **준비 집합 계산.** 의존성이 모두 통과한 태스크들이 곧 병렬 실행 후보다.

`orchestra/dispatch.mjs`의 `assertAcyclic()`과 `depsSatisfied()`가 정확히 이 둘이다.

### 재개 가능성

크래시나 중단 후 처음부터 다시 시작하면 태스크 시스템이 아니다.
상태를 매 태스크 완료마다 디스크에 flush 해야 한다:

```js
results.set(id, result);
ctx.state.tasks[id] = result;
await saveState(ctx.state);   // 매 완료마다
```

Meta의 REA(Ranking Engineer Agent)는 이걸 극단까지 밀어붙인 사례다 —
6시간짜리 태스크를 **hibernate-and-wake 체크포인팅**으로 재개한다.
개별 턴이 컨텍스트 한도를 넘어도 파이프라인 전체는 며칠에 걸쳐 일관성을 유지한다.

### 실패 모드

- **상태를 끝에만 저장.** 중간에 죽으면 전부 잃는다.
- **락 없음.** 두 워커가 같은 태스크를 동시에 집는다.
- **의존성 사이클을 런타임에 발견.** 교착으로 나타나서 디버깅이 어렵다.
- **실패한 태스크의 산출물을 버림.** 절반짜리 작업도 다음 판단에 유용하다.

## §13 · 백그라운드 실행 — 메인 루프 밖에서 어떻게 도는가

> **느린 작업을 메인 루프 밖에서 시작하고 나중에 보고받는다.**

1. 어떤 작업이 블로킹 없이 돌 수 있는지 정한다.
2. 시작하고 **핸들을 즉시 반환**한다.
3. running / completed / failed / killed 상태를 추적한다.
4. 나중에 **완료 메시지를 루프로 되돌려 보낸다**.

### 왜 폴링하면 안 되는가

```
❌ 나쁨:  작업 시작 → sleep 5 → 상태 확인 → sleep 5 → 상태 확인 → ...
✅ 좋음:  작업 시작 → 핸들 반환 → 다른 일 → [완료 알림이 루프를 깨움]
```

폴링은 토큰과 벽시계를 둘 다 태운다. 하네스가 완료를 추적할 수 있으면
**알림이 루프를 깨우게** 해야 한다. 하네스가 추적할 수 없는 외부 작업(CI 실행,
배포)만 폴링 대상이고, 그때도 간격은 대상의 실제 변화 속도에 맞춘다.

### 동시성 풀

무한 fan-out은 레이트 리밋과 메모리를 터뜨린다. 풀 크기를 두고
`Promise.race`로 슬롯이 비는 대로 다음 작업을 넣는다:

```js
while (pending.size > 0 || running.size > 0) {
  for (const id of [...pending]) {
    if (running.size >= ctx.concurrency) break;
    if (!depsSatisfied(id)) continue;
    running.set(id, runTask(byId.get(id), ctx));
  }
  const { id, result } = await Promise.race(running.values());
  running.delete(id);
  results.set(id, result);
}
```

**교착 방지가 중요하다.** 실행 중인 것도 없고 대기 중인 것이 시작될 수도 없으면
무한 루프가 된다. 그 상태를 감지해서 남은 걸 `blocked`로 마감해야 한다.

### 실패 모드

- **핸들 없이 시작.** 죽일 수도, 상태를 물을 수도 없다.
- **타임아웃 없음.** 멈춘 자식이 슬롯을 영원히 점유한다.
- **완료 알림 유실.** 작업은 끝났는데 루프가 모른다.
- **교착 미감지.** 준비되는 태스크가 없는데 루프가 계속 돈다.

## §14 · 스케줄링 — 나중에 어떻게 실행되는가

> **유저 입력이 아니라 시계로부터 에이전트 턴을 시작한다.**

1. 스케줄을 한 턴 **바깥에** 저장한다.
2. 루프와 **독립적으로** 시간을 감시한다.
3. 스케줄이 발화하면 프롬프트를 **큐에 넣는다**.
4. 선택적으로 재시작을 넘어 **지속**시킨다.

### 루프 종류의 분류

Anthropic의 루프 taxonomy가 유용하다:

| 루프 종류 | 트리거 | 예 |
| --- | --- | --- |
| **턴 기반** | 유저 메시지 | 일반 대화 |
| **목표 기반** | 목표 달성까지 | `/goal` |
| **시간 기반** | 시계 | `/loop`, `/schedule`, cron |
| **선제적** | 외부 이벤트 | 웹훅, 채널 메시지 |

**작업 모양에 맞는 루프 프리미티브를 고르는 것**이 요점이고,
어느 쪽이든 **결정론적 정지 조건과 토큰 예산**이 필요하다.

### 스케줄링이 §21로 이어지는 지점

스케줄은 그 자체로는 별거 아니다 — cron이다.
중요한 건 **사람이 프롬프트를 치지 않아도 실행이 시작된다**는 것이고,
그게 §21에서 "사람이 외부 루프에서 빠지는" 전제가 된다.

### 실패 모드

- **스케줄이 인메모리.** 재시작하면 사라진다.
- **중첩 실행.** 이전 실행이 안 끝났는데 다음이 시작된다 → 락 필요 (§12).
- **타임존 혼동.** cron은 보통 UTC다. 로컬 시각을 그대로 넣으면 어긋난다.
- **발화만 하고 결과를 아무도 안 봄.** §20의 리포팅이 없으면 조용히 실패한다.

## §15 · 워크트리 격리 — 병렬 작업이 어떻게 충돌을 피하는가

> **병렬 에이전트에게 각자의 작업 디렉터리를 준다.**

1. 작업 단위마다 **사설 체크아웃**을 만든다.
2. 툴을 그 체크아웃에 **바인딩**한다.
3. 워크트리 루트를 **탈출하는 경로를 거부**한다.
4. **깨끗한 워크트리는 제거하고, 더러운 것은 리뷰용으로 남긴다.**

### 왜 브랜치가 아니라 워크트리인가

| | 브랜치 전환 | 워크트리 |
| --- | --- | --- |
| 작업 디렉터리 | **하나를 공유** | 각자 분리 |
| 동시 실행 | 불가 (서로 덮어씀) | 가능 |
| `.git` | 공유 | **공유** (그래서 브랜치는 즉시 보인다) |
| 비용 | 없음 | 체크아웃 하나만큼의 디스크 |

`git worktree add -b orchestra/<id> <dir> <base>` 하나면 격리가 끝난다.
같은 오브젝트 데이터베이스를 쓰므로 브랜치는 즉시 공유되고,
**파일 충돌은 병합 시점까지 미뤄진다.**

### 4번 규칙이 중요한 이유

```js
if (await worktreeIsClean(dir)) {
  await removeWorktree(dir);   // 리뷰할 게 없다
}
// 더러우면 남긴다 — 커밋 안 된 작업을 조용히 버리지 않는다
```

정리 자동화가 **사람이 아직 안 본 작업물을 지우는 것**이 가장 흔한 사고다.
`orchestra/dispatch.mjs`는 실패한 태스크의 산출물도 커밋한 뒤 정리한다.

### 실패 모드

- **경로 탈출.** 툴이 `../../`로 다른 워크트리를 건드린다.
- **stale 워크트리 재사용.** 중단된 실행의 잔재가 다음 실행에 섞인다.
  → 생성 전에 강제 제거하는 게 안전하다.
- **깨끗한지 안 보고 지움.** 작업물 유실.
- **같은 파일을 두 태스크가 건드림.** 격리는 되지만 병합에서 터진다 —
  **분해가 잘못된 신호다.**

## §16 · 코디네이션 — 여러 에이전트가 어떻게 대화하는가

> **리드가 작업 크기에 맞춰 팀을 구성하고, 팀원을 각자의 스레드에 스폰하고,
> 공유 인박스로 대화한다.**

1. 에이전트에게 **안정적인 주소**를 준다.
2. 리드가 작업에 맞게 **팀을 편성**한다.
3. 리드가 각 팀원을 **자기 스레드에** 스폰한다.
4. 각 팀원이 **자기 인박스를 당겨서** 스크립트 없이 행동한다.
5. 게이팅된 행동을 **사람 승인자에게 버블링**한다.

### 서브에이전트(§6)와의 차이

| | §6 서브에이전트 | §16 코디네이션 |
| --- | --- | --- |
| 관계 | 부모→자식, 단방향 | 피어, 양방향 |
| 수명 | 한 작업 | 세션에 걸침 |
| 통신 | 반환값 한 번 | 인박스, 지속적 |
| 주소 | 없음 | **있음** |

**주소가 있느냐**가 결정적이다. 주소가 있으면 리드를 거치지 않고 피어끼리 대화할 수 있고,
그때부터 시스템은 분산 시스템의 성질을 갖는다.

### 그리고 분산 시스템은 어렵다 ⚠️

GitHub이 정리한 실패 패턴:

> 멀티 에이전트 시스템은 **분산 시스템처럼 행동한다.**
> 그래서 모든 핸드오프에 타입 스키마, 제한된 액션 스키마, 명시적 경계 검증이 필요하다.

"에이전트를 더 추가하자"를 **인터페이스 설계 문제**로 바꿔 놓는 게 이 관점의 값어치다.

### 토폴로지 선택

| 토폴로지 | 언제 |
| --- | --- |
| **서브에이전트** | 컨텍스트 격리가 목적. 멀티 도메인에서 토큰 67% 절감 |
| **스킬** | 절차가 짧고 반복적 |
| **핸드오프** | 작업이 단계별로 완전히 넘어감 |
| **라우터** | 입력에 따라 하나를 고르면 됨 |

**토폴로지 변경이 모델 변경보다 나은 레버인 경우가 많다.**
AdaptOrch 같은 연구는 토폴로지를 작업 의존성 그래프에 따라 동적으로 고르면
모델 선택만으로는 못 얻는 12–23% 개선이 있다고 보고한다.

### 실패 모드

- **메시지 스키마 없음.** 자유 텍스트 핸드오프가 조용히 오해된다.
- **리드가 병목.** 모든 통신이 리드를 거치면 리드 컨텍스트가 터진다.
- **승인 버블링 누락.** 팀원이 사람 승인 없이 위험한 행동을 한다.
- **팀이 너무 큼.** 조율 비용이 병렬화 이득을 넘는다.

## §17 · 프로토콜 — 합의하고 깔끔히 멈추기

> **메시지에 계약을 준다: 행동 전에 승인, 정지 전에 확인.**

1. 요청과 응답에 **타입 있는 형태**를 준다.
2. 각 응답을 **원 요청과 상관**시킨다.
3. 위험한 계획을 작업 시작 **전에** 게이팅한다.
4. 진행 중인 작업을 잃지 않고 에이전트를 **정지**시킨다.
5. 하나의 워커가 이기면 **팬아웃 전체를 정지**시키고, 그 경쟁을 **정확히 한 번** 정산한다.
6. 신뢰 경계를 넘어 팀 밖 에이전트에 **도달**한다.

5번이 미묘하다. 병렬 탐색에서 하나가 답을 찾았을 때 나머지를 죽여야 하는데,
**"정확히 한 번"** 정산하지 않으면 두 워커가 동시에 이겼다고 보고한다.

### 신뢰 경계

6번이 보안 지점이다. 팀 밖 에이전트에서 오는 메시지는 **신뢰 불가 입력**이다.
§2의 치명적 3요소가 여기서 다시 나온다 —
외부 에이전트 메시지가 지시처럼 읽히면 프롬프트 인젝션의 벡터가 된다.

> **규칙:** 외부에서 온 텍스트는 데이터로 취급하고, 그 안의 지시를 따르지 않는다.
> 작업 방향을 바꾸려는 것처럼 보이면 사람에게 확인한다.

### 실패 모드

- **상관 ID 없음.** 어느 응답이 어느 요청의 것인지 모른다.
- **정지 시 in-flight 작업 유실.** graceful shutdown 핸드셰이크 없음.
- **경쟁 이중 정산.** 두 승자가 각각 부작용을 일으킨다.
- **외부 메시지를 지시로 취급.** 프롬프트 인젝션.

## §18 · 자율성 — 스스로 어떻게 조직화하는가

> **사람 프롬프트 없이 루프를 돈다: 유휴 시 보드를 스캔하고, 준비된 태스크를 점유하고, 작업한다.**

1. 할 일이 없음을 알아챈다 (작업 단계가 `end_turn`에 도달).
2. 공유 보드에서 **주인 없고 막히지 않은** 태스크를 본다.
3. 다른 유휴 에이전트와 **경쟁하지 않고** 하나를 점유한다.
4. 점유한 태스크로 루프에 재진입하고, 보드가 빌 때까지 반복한다.

### 이건 §12 + §14 + §16의 조합이다

새 프리미티브가 없다. 지속 태스크 보드(§12), 유휴를 트리거로 쓰는 것(§14),
주소와 점유(§16)를 엮으면 자율 루프가 된다.

### 점유(claim)는 원자적이어야 한다

```
❌  if (task.owner == null) { task.owner = me; }   // 두 워커가 동시에 통과
✅  원자적 compare-and-swap 또는 파일 락
```

두 에이전트가 같은 태스크를 집으면 같은 작업을 두 번 하고, 최악의 경우
같은 부작용을 두 번 일으킨다.

### 성숙도와 권한은 같은 결정이다

자율성을 올린다는 건 §3의 권한을 여는 것이다. §21의 성숙도 레벨(L1 보고 /
L2 보조 / L3 무감독)이 바로 그 눈금이고, **현재 레벨에서 지루할 만큼 정확했을 때만**
한 단계 올린다.

### 실패 모드

- **점유가 원자적이지 않음.** 중복 실행.
- **유휴 감지가 너무 공격적.** 사람이 다음 지시를 타이핑하는 중에 새 작업을 시작한다.
- **보드가 비어도 계속 스캔.** 유휴 폴링이 비용을 먹는다 → 백오프 필요.
- **자율 루프에 리포팅 없음.** 아무도 안 볼 때 실패하면 발견되지 않는다 (§20).

## 이 레이어를 제거할 수 있는 조건

| 레이어 | 존재 이유 | 제거 가능 시점 |
| --- | --- | --- |
| §12 태스크 지속 | 세션이 죽으면 작업이 사라짐 | 제거 불가 (인프라 성질) |
| §13 동시성 풀 | 레이트 리밋과 메모리가 유한 | 제거 불가 |
| §14 스케줄 | 사람이 없어도 시작해야 함 | 제거 불가 (요구사항) |
| §15 워크트리 | 병렬 에이전트가 충돌 | 런타임이 격리를 기본 제공하면 |
| §16 코디네이션 | 한 루프가 감당 못 하는 규모 | 컨텍스트가 무한하면 단일 루프로 회귀 가능 |
| §17 프로토콜 | 분산 시스템의 성질 | 제거 불가 |
| §18 자율성 | — | 이건 **능력이 아니라 선택**이다 |

Layer 4–5는 앞 레이어들과 성격이 다르다.
**대부분이 "모델이 못 해서"가 아니라 "분산 시스템이라서" 존재한다.**
그래서 모델이 좋아져도 거의 그대로 남는다.
