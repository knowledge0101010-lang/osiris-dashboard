# 07 · 하네스 지형도

강의를 마치고 "그래서 뭘 써야 하나"에 답하기 위한 지도.
2026년 시점에서 하네스는 **프레임워크 인기 투표가 아니라 설계 트레이드오프의 비교**다.

---

## 1. 계층 — 어디까지 직접 만들 것인가

```
┌─ 완제품 에이전트 ────────────────────────────────────────┐
│  Claude Code · Codex CLI · Cursor · Deep Agents Code     │
│  하네스 전체가 이미 있음. 설정과 확장만 한다              │
├─ 배터리 포함 하네스 ─────────────────────────────────────┤
│  Deep Agents · Flue · Hive                               │
│  루프·파일시스템·서브에이전트·스킬이 기본 제공            │
├─ 최소 하네스 ────────────────────────────────────────────┤
│  LangChain create_agent · OpenAI Agents SDK · PydanticAI │
│  루프와 툴 계약만. 나머지는 직접                          │
├─ 런타임 / 그래프 ────────────────────────────────────────┤
│  LangGraph · Apache Burr · Temporal 기반 (Shannon)       │
│  루프 모양 자체를 직접 정의. 체크포인팅·지속성 제공        │
├─ 프로토콜 / SDK ─────────────────────────────────────────┤
│  Anthropic SDK · MCP · Codex SDK                         │
│  모델 호출과 툴 계약. 루프는 전부 직접                    │
└──────────────────────────────────────────────────────────┘
```

**선택 기준은 "루프의 모양이 맞는가"다.**

| 상황 | 계층 |
| --- | --- |
| 코딩 작업을 지금 처리해야 함 | 완제품 |
| 도메인 에이전트를 만드는데 루프는 표준적 | 배터리 포함 |
| 루프는 표준적인데 미들웨어를 많이 붙일 것 | 최소 하네스 |
| 제어 흐름이 대부분 이미 알려짐 (§22) | 그래프 런타임 |
| 배우려고 / 극단적으로 가벼워야 함 | SDK 직접 |

## 2. 세 개의 참조 하네스 — 이 노트가 근거로 삼은 것

`awesome-agent-architecture`가 24개 섹션 전체에서 나란히 비교하는 세 시스템.

| | Claude Code | Hermes Agent | mini-swe-agent |
| --- | --- | --- | --- |
| 성격 | 프론티어 코딩 에이전트 | 장기 어시스턴트 | 연구 베이스라인 |
| 크기 | 하네스가 코드의 대부분 | 중간 | **에이전트 클래스 ~150줄** |
| 커버 섹션 | 0–23 (전부) | 7, 9, 14, 16, 19, 21, 22 | 0–3, 8, 10, 11, 20–23 |
| 툴 | 다수 + MCP | 스킬 중심 | **bash 하나** |
| 정지 신호 | `stop_reason: end_turn` | — | `role: "exit"` 마커를 환경이 감지 |
| 병렬 툴 | O | — | X |
| 스트리밍 | O | — | X |
| 권한 게이트 | O | O | 확인 게이트 + 스텝/비용 예산 |

**mini-swe-agent를 반드시 보라.** 하네스가 거의 없는 극단이 있어야
"하네스가 무엇을 사는지"가 뺄셈으로 보인다.

- 장점: 유지보수할 게 거의 없다. 감사가 쉽다.
- 단점: bash 실행을 넘는 모든 능력이 모델에서 나와야 한다.
- 전제: 작업이 **컨텍스트가 차기 전에** 제출 또는 비용 한도로 끝난다.

## 3. Deep Agents — "배터리 포함 하네스"의 대표

LangChain의 `deepagents`는 이 노트의 섹션 대부분을 기본 제공한다.

| 기능 | 대응 섹션 |
| --- | --- |
| Sub-agents (격리된 컨텍스트 윈도우) | §6 |
| Filesystem (로컬/샌드박스/원격 백엔드) | §9 |
| Context management (요약 + 툴 출력 디스크 오프로드) | §8 |
| Shell access | §2, §3 |
| Persistent memory (state/store 백엔드 교체 가능) | §9, §12 |
| Human-in-the-loop (툴 호출 승인/편집/거부) | §3 |
| Skills | §7 |
| Tools + MCP | §2, §19 |

### 계층 관계

```
LangGraph            그래프 런타임 (§22)
   └─ create_agent   최소 하네스
        └─ deepagents  의견 있는 하네스 (파일시스템·서브에이전트·컨텍스트·스킬 포함)
```

**세 층이 조합된다** — 어떤 LangGraph `CompiledStateGraph`든 Deep Agent의
서브에이전트로 넘길 수 있다. 커스텀 오케스트레이션이 하네스 기본값 옆에 꽂힌다.

### 원칙 4가지

1. **Opinionated** — 장기·멀티스텝 작업에 맞춘 기본값
2. **Extensible** — 포크 없이 어느 부품이든 교체
3. **Model-agnostic** — 툴 호출을 지원하는 모든 LLM (프론티어/오픈웨이트/로컬)
4. **Production-ready** — 스트리밍·지속성·체크포인팅 + 트레이싱·평가·배포

### 보안 모델 — 명시적으로 "모델을 신뢰한다"

> Deep Agents는 "trust the LLM" 모델을 따른다.
> 에이전트는 **툴이 허용하는 건 뭐든 할 수 있다.**
> 경계는 **툴/샌드박스 레벨에서 강제**하라. 모델의 자기 규율을 기대하지 마라.

§3의 요지와 정확히 같고, 이걸 문서에 명시한 게 좋은 하네스의 표시다.

### 출처 인정

> "Claude Code에서 영감을 받음: 무엇이 그것을 범용으로 만드는지 식별하고,
> 그것을 더 밀어붙이려는 시도."

## 6. 지형도를 읽는 원칙

1. **하네스 변경이 모델 변경보다 큰 레버인 경우가 많다.**
   같은 모델로 벤치마크 30위 → 톱5, 비용 1/10로 동급 성능 —
   전부 하네스 튜닝 결과다.

2. **프레임워크 인기 ≠ 적합성.**
   70개 프로젝트 중 60%가 Agent Loop 패턴을 쓰지만,
   그게 당신 작업에 맞다는 뜻은 아니다 (§22).

3. **모델과 하네스는 공진화한다.**
   특정 하네스로 학습된 모델은 그 설계에 과적합될 수 있다.
   그래서 하네스 아키텍처 선택은 당장의 작업을 넘어 오래 간다.

4. **평가가 하네스 작업의 학습 데이터다.**
   평가 없이 프레임워크를 고르는 건 취향 표명이다.

5. **모든 부품에 제거 조건을 적어라.**
   지금 필요한 하네스가 다음 모델 세대에는 부채다. 목록이 있어야 지운다.
