## §21 · 루프 엔지니어링 — 루프가 어떻게 스스로 도는 시스템이 되는가

> **다음 프롬프트를 쓰지 마라. 당신 없이 에이전트를 돌리는 루프를 설계하라.**

### 무엇이 바뀌는가

엔지니어링 노력이 놓이는 자리가 바뀐다.
턴마다 프롬프트를 쓰는 대신, **작업을 발견하고 · 에이전트를 돌리고 ·
출력을 검사하고 · 다음에 무엇을 할지 정하는** 외부 시스템을 만든다.

> **사람이 운영자에서 설계자로 이동한다.**

이 레이어가 없으면 **사람이 곧 외부 루프다.** 사람이 프롬프트하고, 읽고,
판단하고, 손으로 재시도한다. 그리고 사람이 멈추는 순간 에이전트도 멈춘다.

### 네 개의 중첩 루프

```text
┌─ 개선 루프 ─────────────────────────────────────────────┐
│  트레이스·평가 → 하네스 설정/스킬/모델 변경              │
│  "시스템이 나아지고 있는가?"                             │
│  ┌─ 이벤트 루프 ────────────────────────────────────┐   │
│  │  cron · 웹훅 · 채널이 실행을 시작                  │   │
│  │  "작업은 언제 시작되는가?"                         │   │
│  │  ┌─ 검증 루프 ─────────────────────────────────┐ │   │
│  │  │  루브릭으로 채점, 실패는 피드백과 함께 재시도 │ │   │
│  │  │  "진짜로 다 됐는가?"                          │ │   │
│  │  │  ┌─ 에이전트 루프 (§1) ───────────────────┐  │ │   │
│  │  │  │  다 된 것처럼 보일 때까지 툴 호출        │  │ │   │
│  │  │  │  "한 스텝이 어떻게 완료되는가?"          │  │ │   │
│  │  │  └────────────────────────────────────────┘  │ │   │
│  │  └─────────────────────────────────────────────┘ │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

데이터는 **바깥으로** 흐른다. 트리거가 발화해서 프롬프트를 큐에 넣는다.
에이전트 루프가 후보를 만든다. 채점자가 점수를 준다. 실패는 피드백을 붙여
예산이 남는 동안 재시도한다. 통과는 작업의 채널로 배달된다.
실행 트레이스는 텔레메트리로 가고, 개선 루프가 그걸 읽는다.

### 검증 루프 — 앞 섹션들이 만들지 않은 유일한 루프

내부 루프는 **모델이 다 됐다고 말할 때** 멈춘다.
검증 루프는 "다 됐다"를 **검사된 주장**으로 만든다.

```python
def verified_run(task, worker, checker, budget=2):
    budget = max(1, budget)                    # 0이면 한 번도 안 돌고 실패로 끝난다
    feedback = ""
    attempts = []
    for n in range(1, budget + 1):            # 천장: 하네스가 강제
        out = worker(task + feedback)          # 내부 루프 (§1)
        verdict = checker(task, out)           # 별도 채점자 (§6)
        attempts.append({"attempt": n, "passed": verdict["passed"], "reason": verdict["reason"]})
        if verdict["passed"]:
            return {"ok": True, "output": out, "attempts": attempts}
        feedback = f"\n\n이전 시도가 거부됨. 실패 사유: {verdict['reason']}"
    return {"ok": False, "output": None, "attempts": attempts}   # 예산 소진: 에스컬레이션
```

네 가지 설계 결정이 들어 있다.

| 결정 | 이유 |
| --- | --- |
| **채점자는 새 컨텍스트를 가진 별도 에이전트** | 자기 출력을 자기가 채점하면 통과시킨다 |
| **루브릭은 루프 밖에 고정** | 모델이 만족시킬 수는 있어도 다시 쓸 수는 없다 |
| **피드백은 데이터** | 실패 판정이 재시도 프롬프트에 실려 들어간다. 2차 시도는 1차가 뭘 틀렸는지 안다 |
| **`ok: False`는 에스컬레이션 신호** | 시도 기록이 사람에게 간다. 영원히 재시도하지 않는다 |

**이 레포의 구현은 위 표의 축소판이다.** 차이를 분명히 해 둘 값어치가 있다.

| | 위 개념 모델 | [`orchestra/dispatch.mjs`](../../orchestra/dispatch.mjs) |
| --- | --- | --- |
| 채점자 | 새 컨텍스트를 가진 **별도 에이전트** | **셸 명령 검증자** — `runCodex` 뒤에 `verify()`가 종료 코드로 판정 |
| 루브릭 | 루프 밖의 문장 | 루프 밖의 **명령어** (`board.json`의 `verify`) |
| 피드백 | 판정문 | 실패 출력 tail이 `retryPrompt()`로 |
| 예산 | `range(budget + 1)` | `Math.max(1, verifyRetries + 1)` |

**셸 검증자는 별도 에이전트보다 약하다.** 종료 코드는 "체크를 통과시키려고
체크를 약화시킨" 경우를 못 잡는다. 그래서 이 레포는 그 자리를
[`codex-liaison`](../../.claude/agents/codex-liaison.md) 서브에이전트에게 맡긴다 —
그게 표의 "별도 채점자" 역할이고, diff를 브리프와 대조한다.

### 예산과 정지 조건

> **모든 루프에는 모델이 말로 넘어설 수 없는 천장이 필요하다.**

- 반복 횟수
- 토큰 예산
- 벽시계 한도
- **dry counter** — 새로운 걸 못 찾은 라운드가 K번이면 정지

`verified_run`에서 천장은 `range()`의 상한이다.
**`budget + 1` 번째 시도는 일어날 수 없다.**

모델에게 "제발 멈춰줘"라고 하는 건 힌트지 정지 조건이 아니다.

### 성숙도 레벨

루프를 얼마나 신뢰하느냐로 등급을 매긴다.

| 레벨 | 루프가 하는 일 | 사람이 하는 일 |
| --- | --- | --- |
| **L1 · 보고** | 읽고 보고한다 | 행동한다 |
| **L2 · 보조** | 변경을 초안 잡는다 | 승인한다 |
| **L3 · 무감독** | 행동한다 | 사후 감사한다 |

**레벨은 권한 결정(§3)이다.**
현재 레벨의 출력이 **지루할 만큼 정확했을 때만** 한 단계 올린다.

이 레포의 `/orchestra` 커맨드는 L2다 — 워커가 브랜치에 초안을 만들고,
사람(또는 지휘자)이 병합을 승인한다. L3으로 올리려면 자동 병합을 켜야 하는데,
그건 검증 루프가 오래 지루했던 뒤의 결정이다.

### 개선 루프의 성숙한 형태

가장 바깥 루프가 성숙하면 **하네스 자체를 편집한다**:

1. 트레이스에서 약점을 채굴한다.
2. 경계가 있는 편집을 제안한다.
3. 회귀 세트에 대해 검증한다.

이 지점에서 **루프 구조가 손으로 만든 템플릿이 아니라 탐색 공간이 된다.**

### 구성 요소는 전부 앞 섹션이다

| 부품 | 어디서 |
| --- | --- |
| 트리거 | §14 스케줄, §19 채널 |
| 워커 | §1 루프, §6 서브에이전트(제작자/검증자 분리) |
| 병렬 격리 | §15 워크트리 |
| 실행 간 상태 | §9 메모리, §12 태스크 레코드 |
| 리포트와 트레이스 | §20 관측성 |

**§21은 새 프리미티브를 추가하지 않는다.** 조합이다.

### 실패 모드

- **자기 채점.** 워커가 자기 출력을 채점하면 통과율이 무의미해진다.
- **루브릭이 루프 안에 있음.** 모델이 기준을 바꿔서 통과한다.
- **예산 없음.** 무한 재시도로 비용이 소각된다.
- **에스컬레이션 경로 없음.** 실패가 조용히 묻힌다.
- **너무 빨리 L3.** 감사할 사람 없이 자율 실행을 켜면 실패가 누적된다.
- **검사를 약화시켜 통과.** 종료 코드로는 안 잡힌다 → diff 리뷰가 필요하다.

## §22 · 그래프 엔지니어링 — 제어 흐름이 언제 모델에서 코드로 옮겨가는가

> **다음에 뭐가 실행될지 모델에게 묻지 마라. 이미 아는 경로는 인코딩하고,
> 판단이 필요한 곳에만 모델을 써라.**

### 네 가지 개념

1. **노드가 일을 한다.** 노드는 평범한 코드일 수도, 모델 호출 하나일 수도, 에이전트 실행 전체일 수도 있다.
2. **엣지가 다음 노드를 고른다.** 하네스가 **코드로** 평가한다. 모델 호출이 아니다.
3. **사이클이 허용된다.** 재시도, 리뷰 후 수정, 사람 대기 — 전부 되돌아가는 경로가 필요하다.
4. **상태는 그래프를 통과하는 하나의 레코드다.** 각 노드가 읽고 자기 갱신을 쓴다.

### 언제 루프에서 그래프로 가는가

| 신호 | 함의 |
| --- | --- |
| 경로를 **이미 안다** | 모델에게 물을 이유가 없다. 엣지로 인코딩하라 |
| 같은 순서가 **매번 반복**된다 | 모델이 매번 그 결정에 토큰을 쓴다 |
| 순서를 **틀리면 안 된다** | 확률적 결정보다 코드가 낫다 |
| 단계마다 **다른 모델/설정**이 맞다 | 노드마다 다르게 줄 수 있다 |

반대로 **판단이 필요한 지점에는 모델을 남긴다.** 그게 요점이다 —
그래프는 모델을 없애는 게 아니라 **모델을 아껴 쓰는** 것이다.

### 상태 머신으로서의 가드레일

`statewright` 같은 프로젝트의 결과가 이 섹션의 논거를 가장 세게 만든다:

> (2차 출처 — [SOURCES](SOURCES.md) §3의 큐레이션 요약 기반, 원논문 미확인)
>
> 워크플로 단계마다 **호출 가능한 툴을 제한**했더니,
> 로컬 모델이 SWE-bench 부분집합에서 2/10 → **10/10**이 되었다.
> 툴 공간을 줄인 것만으로.

**루프 구조가 모델 크기보다 구속적인 제약**이라는 뜻이다.

### 계획을 실행 가능한 코드로

Anthropic의 동적 워크플로가 같은 방향의 다른 표현이다.
Claude가 **JavaScript 오케스트레이션 스크립트를 생성**해서 수십~수백 개의
병렬 서브에이전트에 작업을 팬아웃하고 적대적 검증으로 수렴시킨다.

> 핵심: **계획이 모델의 컨텍스트가 아니라 실행 가능한 코드에 산다.**
> 그래서 한 컨텍스트 윈도우를 넘는 작업까지 에이전트 루프가 확장된다.

이 레포의 [`orchestra/board.json`](../../orchestra/board.json)이 같은 아이디어의
가장 단순한 형태다 — 계획이 대화가 아니라 **데이터 파일**에 있고,
디스패처가 코드로 그걸 실행한다.

### 실행 패턴의 분류

70개 오픈소스 LLM 에이전트 프로젝트 분석에 따르면 **60%가 Agent Loop 패턴**을 쓴다
(arXiv:2604.11378 — 2차 출처, 요약 기반).
나머지는 이벤트 기반, 상태 머신, 그래프/플로, 하이브리드.

선택 기준은 **제어 가능성 / 표현력 / 구현 용이성**의 트레이드오프다:

| 패턴 | 제어 가능성 | 표현력 | 언제 |
| --- | --- | --- | --- |
| Agent Loop | 낮음 | 높음 | 경로를 모를 때 |
| 상태 머신 | 높음 | 낮음 | 단계가 고정이고 틀리면 안 될 때 |
| 그래프 | 중간 | 중간 | 대부분의 경로는 알고 일부만 판단이 필요할 때 |
| 이벤트 기반 | 중간 | 중간 | 외부에서 트리거될 때 |

**가장 단순한 패턴으로 기본값을 두지 마라. 작업 모양에 맞춰라.**

### 그래프가 과한 경우

- 경로를 정말 모를 때. 인코딩할 게 없다.
- 요구사항이 자주 바뀔 때. 그래프 유지보수가 이득을 넘는다.
- 규모가 작을 때. 3단계짜리 그래프는 그냥 함수 세 개다.

### 실패 모드

- **엣지를 모델에게 물음.** 그래프의 요점을 없앤다.
- **사이클 없음.** 재시도와 수정 경로가 막힌다.
- **상태가 노드마다 흩어짐.** 하나의 레코드가 아니면 그래프가 아니라 스파게티다.
- **너무 일찍 그래프화.** 아직 모르는 경로를 고정해서 모델의 판단을 막는다.
- **노드 안이 블랙박스.** 노드가 에이전트 실행이면 그 안은 §20이 필요하다.

## 이 레이어를 제거할 수 있는 조건

| 레이어 | 존재 이유 | 제거 가능 시점 |
| --- | --- | --- |
| §21 검증 루프 | 모델의 "완료" 선언이 신뢰 불가 | 신뢰 가능해져도 **회귀 방지용으로 남는다** |
| §21 예산 천장 | 무한 루프/비용 폭주 | **제거 불가** (비용에 대한 결정) |
| §21 이벤트 루프 | 사람 없이 시작해야 함 | 제거 불가 (요구사항) |
| §21 개선 루프 | 하네스가 저절로 나아지지 않음 | 제거 불가 |
| §22 코드 엣지 | 모델이 매번 같은 결정에 토큰을 씀 | 토큰이 무의미해지면 — 단 **결정론이 필요하면 남는다** |

§22의 마지막 행이 미묘하다. **그래프를 쓰는 이유가 비용이면 사라질 수 있지만,
이유가 "이 순서는 틀리면 안 된다"면 사라지지 않는다.**
자기 그래프가 어느 쪽인지 아는 게 이 레이어의 실력이다.

## 마무리 — §0으로 돌아가기

Layer 7까지 왔으면 §0의 경고를 다시 읽을 때다.

> **하네스는 많을수록 좋은 게 아니다.**
> 모든 레이어는 지금 모델이 못 하는 것을 메운다.
> 모델이 바뀌면 각 레이어를 재평가하라.

그리고 이제 그 재평가를 할 도구가 생겼다 —
**§20의 트레이스와 §23의 평가, 그리고 §21의 개선 루프.**
이게 24개 섹션이 원을 그리며 닫히는 지점이다.
