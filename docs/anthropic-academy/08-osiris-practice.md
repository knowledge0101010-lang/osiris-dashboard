# 08 · OSIRIS 적용 실습

배운 걸 **이 레포에** 적용한다. 읽기만 하면 안 남는다.

---

## 현재 상태 진단

OSIRIS는 Next.js 16 기반 OSINT 대시보드다. AI 관련 코드는 이렇게 생겼다.

```text
src/lib/ai-engine.ts          Gemini 클라이언트 + 프롬프트 조립 + 키 로테이션
src/app/api/ai/analyze/       POST — 인텔리전스 분석
src/app/api/ai/briefing/      POST — 위협 브리핑 생성
src/app/api/ai/overview/      POST — Alerts & Markets AI Overview
```

**하네스 관점의 진단:**

| §섹션 | 현재 | 판정 |
| --- | --- | --- |
| §1 에이전트 루프 | 없음. 단발 `generateContent` 호출 | ❌ 에이전트가 아니라 프롬프트 래퍼 |
| §2 툴 런타임 | 없음. 툴 정의 없음 | ❌ |
| §3 권한 | IP 레이트 리밋(5req/min) — **사용자 권한이지 툴 권한이 아님** | ⚠️ 다른 문제를 푼다 |
| §8 컨텍스트 관리 | 없음. 매 요청이 독립 | ✅ 필요 없음 (단발이므로) |
| §10 프롬프트 조립 | `ai-engine.ts`에서 컨텍스트를 조립 | ⚠️ 캐시 경계 개념 없음 |
| §11 에러 복구 | 키 로테이션 = API 에러 대응 | ⚠️ 부분적 |
| §20 관측성 | 없음 | ❌ |
| §23 평가 | 없음 | ❌ |

> **결론: 지금 OSIRIS의 AI는 하네스가 없다.**
> 그게 나쁜 건 아니다 — 단발 요약에는 루프가 필요 없다.
> **문제는 "루프가 필요한 기능"을 추가할 때 그 결정을 의식적으로 하느냐다.**

이 판단 자체가 §0의 연습이다: **하네스는 많을수록 좋은 게 아니다.**

## 과제 1 · 관측성 먼저 (§20) — 난이도 ★☆☆

**왜 먼저인가:** §20이 없으면 이후 어떤 변경이 개선인지 알 수 없다.
그리고 이건 지금 코드에 가장 적은 침습으로 넣을 수 있다.

**할 일:** `src/lib/ai-engine.ts`의 모든 모델 호출에 구조화된 트레이스를 남긴다.

기록할 것:

```ts
{
  requestId: string,        // 요청 상관 ID
  endpoint: 'analyze' | 'briefing' | 'overview',
  model: string,
  promptTokens: number,     // 사용 가능하면
  completionTokens: number,
  latencyMs: number,
  keyIndex: number,         // 어느 로테이션 키를 썼는지
  outcome: 'ok' | 'rate_limited' | 'error' | 'timeout',
  errorClass?: string,      // §11의 분류
}
```

**하지 말 것:** 프롬프트 본문이나 응답 본문을 그대로 로그에 남기지 마라.
OSINT 데이터가 흘러 들어간다. **관측성이 유출 경로가 되면 안 된다** (§20 실패 모드).

**검증:** 부하를 걸었을 때 어느 엔드포인트가 느린지, 키 로테이션이 실제로
발동하는지 로그만 보고 답할 수 있으면 통과.

## 과제 2 · 에러 분류 (§11) — 난이도 ★☆☆

**현재:** 키 로테이션은 "에러가 나면 다른 키"라는 단일 전략이다.
그건 레이트 리밋에만 맞다.

**할 일:** §11의 4분류를 적용한다.

| 분류 | 현재 코드에서 | 올바른 대응 |
| --- | --- | --- |
| 429 / 503 (레이트 리밋·과부하) | 키 로테이션 | 로테이션 + 지수 백오프 |
| 401 / 403 (키 거부) | 키 로테이션 | **그 키만** 실격 처리. 아래 참조 |
| 400 (요청 자체가 잘못됨) | 키 로테이션 | **로테이션 무의미** — 즉시 실패 |
| 컨텍스트 초과 | ? | 입력 피드를 줄이고 재시도 |
| 응답 파싱 실패 | ? | 재시도 1회, 그 뒤 원문 반환 |

**401은 키 단위인지 계정 단위인지에 따라 갈린다** — 여기가 로테이션 설계의 핵심이다.

- 키들이 **서로 독립적**이면(다른 프로젝트/계정) 401은 **그 키만의 실패**다.
  해당 키를 실격시키고 다음 키로 넘어가는 게 맞다.
- 키들이 **같은 프로젝트·같은 결제 주체**를 공유하면 401은 전부에 대해 참이다.
  이때 로테이션은 모든 키를 태우고 나서야 실패한다 — **첫 401에 즉시 실패**해야 한다.

`.env.example`을 보고 이 레포의 키 풀이 어느 쪽인지 먼저 확정하라. 모르면
"첫 401에 한 번만 로테이션하고, 두 번째 401이면 중단"이 안전한 절충이다.

**400은 다른 문제다.** 라우트 레벨 검증 실패(잘못된 요청 바디)는 Gemini 호출 *전에*
일어나므로 이 분류에 넣으면 안 된다. 두 종류의 400을 분리해서 세라 —
아니면 "모델 에러율" 지표가 클라이언트 실수로 오염된다.

**검증:** 두 가지 테스트를 쓴다.

1. 잘못된 키 N개를 넣고, 공유 계정 설정에서 **N번 시도하지 않고** 즉시 실패하는가
2. 라우트에 잘못된 바디를 보냈을 때 모델 에러 카운터가 **안 올라가는가**

## 과제 3 · 평가 환경 (§23) — 난이도 ★★☆

**할 일:** `src/lib/ai-engine.ts`의 브리핑 생성에 대한 평가 환경을 만든다.

5요소를 채운다:

| 요소 | OSIRIS에서 |
| --- | --- |
| **데이터셋** | 고정된 인텔리전스 컨텍스트 스냅샷 10개 (지진/뉴스/사이버/충돌 조합) |
| **환경 상태** | 없음 — 브리핑은 읽기 전용. **리셋 불필요** |
| **툴** | 없음 (단발 호출) |
| **루브릭** | 아래 참조 |
| **프로토콜** | 단일 턴 |

루브릭을 §23의 3갈래로 쪼갠다:

- **결과:** 심각도 CRITICAL 이벤트가 브리핑에 **전부** 언급되었는가 → **코드로 검사 가능**
- **과정:** (해당 없음 — 툴 호출이 없다)
- **품질:** 브리핑이 상호 연관을 만들었는가, 좌표/시각이 정확한가 → LLM 채점자

**중요:** 결과 검사를 코드로 짜라. LLM 채점자에게 "CRITICAL이 다 들어갔나"를
물으면 놓친다. **코드가 검사할 수 있는 건 코드로 검사한다.**

**Pass^k:** 각 데이터셋 항목을 3회 돌려서 3회 다 통과해야 통과로 친다.
브리핑은 비결정적이므로 1회 실행은 운을 측정한다.

**검증:** 프롬프트를 일부러 나쁘게 바꿨을 때 점수가 내려가면 평가가 작동하는 것이다.
안 내려가면 루브릭이 아무것도 안 재고 있다.

## 과제 4 · CLAUDE.md 작성 (§10) — 난이도 ★☆☆

`.gitignore`가 `CLAUDE.md`를 무시하므로 로컬에 만든다.

**규칙:** "모델이 일반 지식으로 알 만한 것"은 빼고 **이 레포에서만 참인 것**만.

초안:

```markdown
# OSIRIS

Next.js 16 (App Router) + React 19 + Tailwind 4. OSINT 대시보드.

## 명령
- 개발: `npm run dev`
- 테스트: `npm run test` (vitest). 라이브 API 테스트: `npm run test:live`
- 린트: `npm run lint`

## 이 레포의 규칙
- 외부 fetch는 반드시 `src/lib/ssrf-guard.ts`를 거친다. 우회하지 말 것
- API 라우트는 `export const dynamic = 'force-dynamic'` 필요
- `src/lib/ai-engine.ts`는 Gemini를 쓴다. 다른 프로바이더를 섞지 말 것
- 새 데이터 소스는 `src/app/api/<name>/route.ts` + 레이트 리밋 필수
- `intel/`은 정적 데이터. 코드에서 쓰기 금지

## 하지 말 것
- 프롬프트/응답 본문을 로그에 남기지 말 것 (OSINT 데이터 유출)
- API 키를 클라이언트 번들에 노출하지 말 것
```

**검증:** 이 파일만 읽고 새 API 라우트를 올바르게 추가할 수 있는가?
못 하면 빠진 게 있다. 반대로 **모델이 원래 아는 내용이 있으면 지워라.**

## 과제 5 · 훅으로 규칙 강제 (§4) — 난이도 ★★☆

과제 4의 규칙 중 **깨지면 안 되는 것**을 훅으로 승격시킨다.

프롬프트 규칙 → 훅 승격 대상:

| 규칙 | 훅 |
| --- | --- |
| SSRF 가드 우회 금지 | `PostToolUse` — 편집된 파일에 raw `fetch(` 가 추가되면 경고 |
| API 키 노출 금지 | `PreToolUse` — `NEXT_PUBLIC_` + `KEY` 조합이 들어가면 차단 |
| 커밋 전 린트 | `PreToolUse` on `git commit` — `npm run lint` 실행 |

**왜 승격하는가:** §4의 요지 — 프롬프트는 모델이 무시할 수 있지만
훅은 하네스 코드가 실행하므로 무시할 수 없다.

**주의:** 훅이 조용히 실패하면 게이트가 없는 것과 같다. 실패를 시끄럽게 만들어라.
그리고 매 툴 호출마다 3초씩 걸리는 훅은 루프 전체를 죽인다.

## 과제 6 · 오케스트라 실전 (§12–15, §21) — 난이도 ★★★

[`orchestra/`](../../orchestra/)를 실제 작업에 쓴다.

**할 일:** 과제 1–3을 오케스트라 보드로 만들어서 Codex 워커들에게 병렬로 시킨다.

```json
{
  "defaults": { "sandbox": "workspace-write", "verifyRetries": 1 },
  "tasks": [
    {
      "id": "ai-tracing",
      "title": "Structured tracing in ai-engine",
      "prompt": "(과제 1의 전체 브리프)",
      "verify": "npm run test -- src/lib && npm run lint"
    },
    {
      "id": "ai-error-classes",
      "title": "Classify AI engine errors",
      "prompt": "(과제 2의 전체 브리프)",
      "dependsOn": ["ai-tracing"],
      "verify": "npm run test -- src/lib"
    },
    {
      "id": "ai-evals",
      "title": "Briefing eval harness",
      "prompt": "(과제 3의 전체 브리프)",
      "dependsOn": ["ai-tracing"],
      "verify": "npm run test -- src/lib/evals"
    }
  ]
}
```

```bash
node orchestra/dispatch.mjs --dry-run    # 항상 먼저
node orchestra/dispatch.mjs -j 2
```

**관찰할 것 — 이게 실습의 진짜 목적이다:**

1. **분해가 맞았는가?** `ai-error-classes`와 `ai-evals`가 같은 파일을 건드려서
   병합 충돌이 났다면 **분해가 틀린 것**이다 (§15 실패 모드). 어떤 경계로
   다시 쪼갤 것인가?
2. **검증이 실제로 뭔가를 잡았는가?** `verifyRetries`가 발동한 태스크가 있나?
   피드백이 2차 시도를 실제로 개선했나? (§21)
3. **워커가 검사를 약화시켰는가?** 통과한 태스크의 diff를 반드시 읽어라.
   테스트 삭제, `.only`, `@ts-ignore`, 린트 비활성화가 있나?
   → `codex-liaison` 서브에이전트를 각 태스크에 돌린다.
4. **`.orchestra/report.md`가 유용했는가?** 아니면 뭐가 빠졌나?

**이 과제의 요점은 코드가 아니라 판단이다.** 자동화가 잘못했을 때
그걸 알아채는 능력이 §21 성숙도의 전부다.
