## §5 · 플래닝 & 투두 — 큰 작업을 어떻게 쪼개는가

> **멀티스텝 작업 전에 계획을 저장하라.**

두 가지 별개의 문제를 푼다.

1. 에이전트는 작업 중에 **현재 체크리스트**가 필요하다.
2. 에이전트는 작업을 이해하기 전에 **파일을 편집하면 안 된다.**

### 플랜 모드 = 권한 상태

플랜 모드는 "계획을 잘 세우라"는 프롬프트가 아니라 **편집 툴이 막힌 상태**다.
계획이 승인되어야 상태가 전이되고 그때 편집 권한이 열린다.
즉 §3(권한)의 응용이지 §5만의 기능이 아니다.

```text
[plan mode]  read/grep/glob 허용 · edit/write 차단
     │
     │  사람이 계획 승인
     ▼
[edit mode]  전체 툴 허용
```

이게 왜 중요한가: "먼저 계획을 세워줘"라고 말로 부탁하는 것과
**편집 툴 자체가 없는 것**은 신뢰도가 다르다. 전자는 확률, 후자는 보장이다.

### 투두 리스트 = 컨텍스트 밖의 작업 상태

투두 리스트는 진행 상황을 **대화가 아니라 구조체**에 둔다.
그래서 압축(§8)이 대화를 잘라내도 "무엇이 남았는가"는 살아남는다.

> **실무 규칙:** 압축을 견뎌야 하는 상태는 대화에 두지 마라.
> 파일이나 투두 구조체에 둬라.

### 장기 작업의 계획 아티팩트

OpenAI Codex 계열에서 나온 패턴이 `PLAN.md` / `IMPLEMENT.md`다.

| 파일 | 내용 | 왜 |
| --- | --- | --- |
| `PLAN.md` | 마일스톤, 각 마일스톤의 **검증 명령**, 범위 안/밖 | 세션이 끊겨도 다음 세션이 이어받는다 |
| `IMPLEMENT.md` | 실행 중 내린 결정과 계획에서 벗어난 지점 | 왜 그렇게 했는지가 남는다 |

Anthropic의 *Effective Harnesses for Long-Running Agents*도 같은 구조다 —
initializer 에이전트가 환경을 한 번 세팅하고, coding 에이전트가 세션마다
점진적으로 진척시킨다. 세션 간 상태는 **기능 목록 + git 커밋 + 테스트 게이트**로 넘어간다.

### 실패 모드

- **계획이 대화에만 있음.** 압축되면 사라진다.
- **마일스톤에 검증 명령이 없음.** "완료"가 주관이 된다.
- **범위 경계를 안 적음.** 에이전트가 인접 코드를 리팩터링하기 시작한다.
- **계획을 너무 잘게 쪼갬.** 모델이 스스로 할 판단을 스크립트로 대체하는 것.

## §6 · 서브에이전트 — 하위 문제를 어떻게 격리하는가

> **집중된 자식 루프를 돌리고 그 결과만 반환한다.**

### 메커니즘

핵심은 **새 `messages[]`** 다.

```text
부모 루프 messages[]  ─────────────────────────────────▶
                        │                          ▲
                        │ 위임                     │ 결과 한 줄
                        ▼                          │
                    [자식 루프: 빈 messages[]]  ────┘
                     탐색 20턴, 파일 40개 읽음
                     ↑ 이 전부가 버려진다
```

자식이 40개 파일을 읽고 20턴을 돌아도 부모 컨텍스트에는 **최종 요약만** 들어온다.
이게 서브에이전트의 전부이고, 다른 모든 특성(전문화, 별도 툴셋, 다른 모델)은 부수적이다.

### 언제 서브에이전트, 언제 스킬인가

LangChain의 측정치가 이 결정을 구체화한다:

> 멀티 도메인 시나리오에서 **서브에이전트가 스킬보다 토큰을 67% 적게 쓴다.**
> 컨텍스트 격리가 도메인 간 부풀림(cross-domain bloat)을 막기 때문이다.

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 넓게 탐색해야 하는데 결론만 필요 | **서브에이전트** | 탐색 과정을 버릴 수 있다 |
| 결과가 부모의 다음 판단에 계속 필요 | 인라인 | 격리하면 다시 읽어야 한다 |
| 절차가 반복되고 짧음 | **스킬** | 위임 오버헤드가 절차보다 크다 |
| 도메인이 여러 개고 서로 무관 | **서브에이전트** | 격리 효과가 가장 크다 |
| 여러 개를 동시에 돌릴 수 있음 | **서브에이전트** | 병렬화는 격리를 전제한다 |

### 검증자로서의 서브에이전트

§21에서 다시 나오는데, 여기서 미리 짚을 값어치가 있다.

> **자기 결과를 자기가 채점하면 통과시킨다.**

그래서 검증자는 **새 컨텍스트를 가진 별도 에이전트**여야 한다.
같은 모델이어도 상관없다 — 중요한 건 작업 과정을 못 봤다는 것이다.
이 레포의 [`.claude/agents/codex-liaison.md`](../../.claude/agents/codex-liaison.md)가
그 구현이다.

### 실패 모드

- **위임 오버헤드가 이득보다 큼.** 3턴짜리 일을 위임하면 손해다.
- **브리프가 불완전.** 자식은 부모 대화를 모른다. 프롬프트에 전부 담아야 한다.
- **결과가 너무 김.** 요약이 원본만큼 길면 격리한 의미가 없다.
- **부모가 결과를 검증 없이 신뢰.** 자식도 틀린다.

## §7 · 스킬 — 능력을 어떻게 온디맨드로 로드하는가

> **스킬은 자립적인 전문성 묶음이다 — 지침 + 스크립트 + 파일. 필요할 때만 로드된다.**

### 요구사항 4가지

1. 사용 가능한 스킬을 **싸게** 나열한다.
2. 선택된 스킬만 **전체 지침을 로드**한다.
3. 스킬이 추가 파일을 가리키되 **자동 로드하지 않게** 한다.
4. built-in / user / project / plugin / MCP 등 **여러 소스에서 발견**한다.

### 점진적 공개 (Progressive Disclosure)

```text
Level 1  name + description        항상 컨텍스트에 (수십 토큰)
            │ 모델이 관련 있다고 판단
            ▼
Level 2  SKILL.md 본문             선택 시 로드 (수백~수천 토큰)
            │ 본문이 파일을 가리킴
            ▼
Level 3  reference.md, 스크립트     모델이 명시적으로 읽을 때만
```

**핵심은 1단계의 비용이다.** 스킬이 50개여도 Level 1 총합이 3천 토큰이면
매 턴 3천 토큰만 낸다. Level 2를 전부 올리면 20만 토큰이 된다.

그래서 **`description` 작성이 스킬 작성의 절반이다.** 모델은 그것만 보고 고른다.
좋은 description은 트리거 조건을 구체적으로 적는다:

```yaml
# 나쁨
description: PDF 관련 작업을 돕습니다

# 좋음
description: >
  PDF 파일이 입력 또는 출력으로 관여하는 모든 작업에 사용.
  텍스트/표 추출, 병합, 분할, 회전, 워터마크, 폼 채우기, OCR 포함.
  사용자가 .pdf 파일을 언급하거나 PDF 산출물을 요구하면 트리거.
```

### 스킬 vs. 툴 vs. MCP 서버

| | 스킬 | 툴 | MCP 서버 |
| --- | --- | --- | --- |
| 형태 | 마크다운 + 파일 | 함수 + 스키마 | 프로세스 + 프로토콜 |
| 로드 시점 | 선택 시 | 항상 (스키마) | 연결 시 (스키마 전부) |
| 담는 것 | **절차 지식** | **능력** | 능력 묶음 + 리소스 |
| 비용 | Level 1만 상시 | 스키마가 상시 | 서버당 스키마 전부 상시 |

**MCP 서버를 여러 개 붙일 때 컨텍스트가 터지는 이유가 마지막 행이다.**
그래서 지연 로딩(deferred tools)이 필요해진다 — §2와 §19에서 다룬 그 문제다.

### 스킬 보안

스킬은 실행 가능한 스크립트를 포함할 수 있다. `SkillTester` 같은 프레임워크가
능력·견고성·**보안** 세 축으로 평가하는 이유다. 툴이 늘어날수록 실패 모드의
조합 폭발이 관리 불가능해진다.

### 실패 모드

- **description이 모호해서 안 불림.** 스킬이 있어도 안 쓰이면 없는 것과 같다.
- **description이 넓어서 아무 때나 불림.** 관련 없는 작업에 수천 토큰이 새어 나간다.
- **SKILL.md에 전부 다 씀.** Level 2가 비대해지면 점진적 공개의 의미가 없다.
- **스킬끼리 충돌.** 두 스킬이 같은 절차를 다르게 규정하면 모델이 흔들린다.

## §8 · 컨텍스트 관리 — 긴 세션이 어떻게 윈도우에 맞는가

> **긴 세션을 컨텍스트 한도 아래로 유지한다.**

### 컨텍스트 부패 (Context Rot)

컨텍스트가 차면 세 가지가 일어난다.

1. API가 요청을 거부한다.
2. 호출이 느려지고 비싸진다.
3. **낡고 덜 유용한 내용이 현재 작업 정보와 경쟁한다.**

세 번째가 **context rot**이다. 관련 없는 텍스트가 쌓이면 모델이 맞는 사실을
덜 찾아낸다. 이건 **윈도우가 차기 훨씬 전부터 시작된다.** 에이전트는 계속 돈다.
그냥 판단이 나빠질 뿐이다.

> **그래서 압축은 "맞추기"와 "비용"만의 문제가 아니다.**
> 인컨텍스트 학습은 추론보다 **검색**에 가깝게 동작한다. 모델은 적혀 있는 사실은
> 찾아낸다. 수십 턴에 흩어진 사실을 조합하는 건 훨씬 못 한다.
> **결론을 한 번 적어 두는 게 매 호출마다 다시 도출하게 하는 것보다 싸다.**
> 좋은 요약은 윈도우에 여유가 있어도 답을 개선한다.

### 계층적 감축 (Claude Code의 순서)

싼 리듀서를 먼저, 요약은 최후에. 요약은 모델 호출 비용이 들고 디테일을 잃는다.

```text
budget    → 거대한 툴 결과를 디스크에 저장하고 프리뷰만 남김   (무손실)
snip      → 낡은 중간 턴을 버리고 head + 최근 tail 유지        (싸다)
micro     → 오래된 tool_result 본문을 스텁으로 교체            (싸다)
collapse  → 선택적 독립 컨텍스트 시스템
auto      → LLM이 전체 히스토리를 한 메시지로 요약             (손실, 최후)
─── 위를 다 해도 prompt_too_long 이면 ───
reactive  → head를 잘라내고 재요약, 재시도 상한 있음
```

**순서가 중요하다.** 큰 툴 결과는 어떤 패스가 본문을 스텁으로 바꾸기 *전에*
디스크에 저장돼야 한다. 안 그러면 영영 못 읽는다.

### 루프 안에 있어야 하는 이유

```python
for _ in range(max_steps):
    messages = context.manage(messages, summarizer=summarizer)   # 매 모델 호출 전
    response = model(messages, registry)
    ...
```

**이 섹션은 루프 본문 자체를 바꾼다.** 앞 섹션들은 툴이나 dispatch를 추가하고
루프는 건드리지 않았다. 컨텍스트 감축은 모든 모델 호출 앞에서 돌아야 하므로
루프 안에 살아야 한다.

### 캐시와 압축은 서로 반대를 원한다 ⚠️

실무에서 가장 자주 놓치는 지점이다.

| | 원하는 것 |
| --- | --- |
| 프롬프트 캐시 | 히스토리를 **건드리지 않는 것** |
| 압축 | 히스토리를 **다시 쓰는 것** |

편집 지점부터 캐시가 무효화되고, 다음 호출은 전체 프리픽스를 다시 읽는다.

- **매 턴 조금씩 다듬으면** → 매 턴 캐시 재구축 (최악)
- **토큰 임계값에서 한 번 크게 줄이면** → 한 번만 재구축 (좋음)

어느 쪽이든 **압축은 API 호출 사이에서 돌아야지, 호출 안에서 돌면 안 된다.**

### 스텁은 매번 바이트 단위로 동일해야 한다

툴 결과를 대체하는 텍스트는 **프리픽스의 일부**다. 첫 교체 때 정하고 그대로 재사용하라.
세션을 디스크에서 복원한 뒤에도 마찬가지다.

타임스탬프나 경로가 매번 다르게 렌더링되는 스텁은 프리픽스를 바꾸고,
**그 뒤의 캐시가 통째로 날아간다.**

### 요약은 "세션 전체"가 아니라 "현재 작업"을 위해 쓴다

일어난 일의 회고록은 다음 호출에 필요한 게 아니다. 질문은 하나다 —
**다음 호출이 아직 필요로 하는 게 뭔가?** 우선순위 순으로:

1. 이미 내린 아키텍처·설계 결정
2. 생성/변경된 파일과 무엇이 바뀌었는지
3. 마지막 검사/테스트의 통과·실패 상태
4. 미해결 TODO와 현재 단계

**원시 툴 출력이 가장 먼저 버려진다.** budget 패스가 이미 큰 결과를 디스크에
써 놨으므로, 정말 필요하면 다시 읽으면 된다.

### CLAUDE.md가 여기서 특별한 이유

압축은 **초기 지침, 중간 결정, 스타일 규칙을 잃는다.** 반면 현재 작업,
최근 에러, 파일 이름은 살아남는 경향이 있다.

> **핵심 규칙은 절대 압축에 의존하지 마라.**
> `CLAUDE.md`로 옮겨라 — 시스템 프롬프트에 살면서 어떤 압축에도 살아남는다.

이게 "왜 CLAUDE.md에 써야 하는가"의 진짜 답이다. 편의가 아니라 **생존성**이다.
자세한 건 [§10](03-layer3-knowledge-resilience.md)에서 이어진다.

### 서버측 압축

Claude API의 컨텍스트 편집 / compaction은 프리픽스에서 오래된 툴 결과를
서버가 떨어뜨린다 — 하네스는 코드를 안 짜도 된다. 다만 **캐시는 한 번 재구축된다.**
그래서 매 턴이 아니라 오버플로 근처에 놓는 게 맞다.

### 실패 모드

- **너무 늦게 압축.** `prompt_too_long`이 나서야 시작하면 작업 도중에 끊긴다.
- **작업 중간에 압축.** 서브태스크 진행 중 요약이 끼면 진행 중인 추론 상태가 깨진다.
  → 에이전트가 스스로 "지금 압축해도 좋다"고 판단하게 하는 방향(autonomous compression)이 나온 이유.
- **요약이 파일 목록을 잃음.** 다음 턴이 어디를 고치던 중인지 모른다.
- **스텁이 불안정.** 캐시가 매번 날아가고 비용이 폭증한다.

## 이 레이어를 제거할 수 있는 조건

| 레이어 | 존재 이유 | 제거 가능 시점 |
| --- | --- | --- |
| §5 플랜 모드 | 모델이 이해 전에 편집을 시작함 | 편집 전 이해가 신뢰 가능해지면 — 단 **승인 게이트로서는 남는다** |
| §5 투두 | 압축이 진행 상태를 잃음 | 압축이 무손실이 되면 |
| §6 서브에이전트 | 컨텍스트가 유한함 | 컨텍스트 비용이 무의미해지면. 단 **병렬화 용도로는 남는다** |
| §7 스킬 | 전체 지식을 상시 로드할 수 없음 | 위와 같음 |
| §8 압축 | 윈도우가 유한함 | 위와 같음. **context rot은 윈도우와 별개로 남을 수 있다** |

이 레이어 전체가 "컨텍스트가 비싸다"는 전제 위에 있다. 그 전제가 흔들리면
레이어 대부분이 부채가 된다 — **단, 승인 게이트(§5)와 병렬화(§6)는 다른 이유로 살아남는다.**
