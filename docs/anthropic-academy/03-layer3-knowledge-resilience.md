# 03 · Layer 3 · 지식과 회복력

> 대응 코스: Claude Code in Action (CLAUDE.md), Building with the Claude API
> 대응 섹션: §9 메모리 · §10 시스템 프롬프트 조립 · §11 에러 복구

Layer 2가 "이번 세션을 윈도우에 맞추는" 문제였다면, Layer 3은
**세션을 넘어서는** 문제다. 무엇을 기억할지, 매 턴 무엇을 다시 조립할지,
그리고 실패했을 때 어떻게 살아남을지.

## §9 · 메모리 — 실행 간에 어떻게 기억하는가

> **지속되는 사실을 대화 밖에 저장한다.**

컨텍스트 관리(§8)와 헷갈리기 쉬운데 **다른 문제**다.

| | §8 컨텍스트 관리 | §9 메모리 |
| --- | --- | --- |
| 범위 | 한 세션 안 | 세션들 사이 |
| 목적 | 윈도우에 맞추기 | 다음 실행이 이어받기 |
| 저장소 | `messages[]` (줄여가며) | 파일, DB, 벡터스토어 |
| 실패 시 | 세션이 죽음 | 매번 처음부터 다시 배움 |

### 4단계

1. **선택 (Selection).** 무엇이 저장할 가치가 있는가.
2. **기록 (Extraction).** 대화 밖에 쓴다.
3. **회수 (Recall).** 관련 있는 것만 불러온다.
4. **정리 (Consolidation).** 낡거나 중복된 항목을 시간이 지나며 청소한다.

각 단계가 독립적인 실패 모드를 갖는다. 4번을 안 하면 메모리는 6개월 뒤
서로 모순되는 사실들의 쓰레기장이 된다.

### 파일시스템이 기본형이다

Microsoft의 Azure SRE Agent 사례가 이 지점을 가장 선명하게 보여준다.
100개 넘는 전용 툴 + 지시적 프롬프트에서, **모든 것을 파일로 노출하고
`read_file` / `grep` / `find` / `shell`을 쓰게 하는 방식**으로 바꿨더니
새로운 인시던트에서 "Intent Met" 점수가 45% → 75%로 올랐다.

이유는 §7의 점진적 공개와 같다. **모델은 이미 파일시스템에 유창하다.**
전용 API를 배우게 하는 것보다 아는 어휘를 쓰게 하는 게 싸다.

LangChain이 하네스의 5대 프리미티브 중 첫 번째로 파일시스템을 꼽는 것도 같은 맥락이다:
파일시스템(지속 상태 + 협업 표면), 코드 실행, 샌드박스, 메모리, 컨텍스트 관리.

### 회수 = RAG를 툴로 만들기

메모리 회수를 "파이프라인 전처리"가 아니라 **툴 호출**로 만드는 게 최근 방향이다.

```text
❌ 파이프라인:  질문 → 검색 → 문서 주입 → 모델 호출
✅ 툴:          모델 → search(query) → 결과 → 모델 → read(chunk) → ...
```

후자는 에이전트의 추론이 **범위를 적응적으로 좁힐 수 있다.**
전자는 주입된 걸 다 처리해야 한다.

### 실패 모드

- **전부 저장.** 회수 정확도가 떨어지고 저장소가 쓰레기가 된다.
- **회수가 너무 넓음.** 관련 없는 기억이 context rot을 만든다.
- **정리 안 함.** 오래된 사실이 새 사실과 모순된다.
- **메모리를 검증 없이 신뢰.** 잘못 추출된 사실이 영구화된다.

## §10 · 시스템 프롬프트 조립 — 매 턴 어떻게 만들어지는가

> **살아 있는 상태로부터 매 턴 프롬프트를 만든다.**

### 왜 조립인가

시스템 프롬프트는 고정된 문자열이 아니다. 매 턴 **섹션들로 조립된다**:

```text
[정적 · 캐시 가능]
  ├─ 코어 아이덴티티와 규칙
  ├─ 툴 사용 지침
  └─ 안전 정책
[프로젝트 · 세션 내 안정]
  ├─ CLAUDE.md / AGENTS.md
  └─ 활성 스킬의 Level 1 목록
[동적 · 매 턴 변함]
  ├─ 현재 작업 디렉터리, git 상태
  ├─ 현재 시각
  ├─ 활성 투두
  └─ 최근 시스템 리마인더
```

세 가지를 얻는다:

1. **새 기능 텍스트가 들어갈 자리가 명확하다.**
2. **비활성 기능 텍스트를 건너뛸 수 있다.**
3. **안정적인 섹션은 프롬프트 캐싱을 쓸 수 있다.**

### 캐시 경계가 순서를 결정한다

```text
┌─────────────────────────┐
│ 정적 (거의 안 변함)      │  ← cache_control 여기
├─────────────────────────┤
│ 프로젝트 (세션 내 고정)  │  ← cache_control 여기
├─────────────────────────┤
│ 동적 (매 턴 변함)        │  ← 캐시 안 됨
└─────────────────────────┘
```

**변하는 것을 뒤에 둔다.** 앞쪽에 시각 같은 걸 넣으면 매 턴 전체 캐시가 무효화된다.

이건 비용 문제만이 아니다. 캐시 미스는 지연시간도 늘리고,
긴 세션에서는 그게 누적되어 체감 성능을 좌우한다.

### 지침 파일 — 압축에서 살아남는 곳

§8에서 짚었지만 여기가 본거지다.

| 규칙을 어디에 두는가 | 압축 후 생존 | 신뢰도 |
| --- | --- | --- |
| 대화 중에 말함 | ❌ 잘려나감 | 낮음 |
| 투두 항목 | ⚠️ 구조체는 남지만 규칙용이 아님 | 중간 |
| 지침 파일 (`CLAUDE.md` / `AGENTS.md`) | ✅ 시스템 프롬프트에 조립됨 | 높음 |
| 훅 (§4) | ✅ 코드가 강제 | **가장 높음** |

**단 "지침 파일"의 생존 방식은 하네스마다 다르다** — 이게 이식 가능한 규칙이 아니다.

| 하네스 | 파일 | 압축 후 |
| --- | --- | --- |
| Claude Code | 프로젝트 루트 `CLAUDE.md` | **압축 후 디스크에서 재주입**된다 |
| Claude Code | 중첩 `CLAUDE.md`, `paths:` 스코프 규칙 | 자동 재주입 **안 됨** — 해당 디렉터리 파일을 다시 읽을 때 살아난다 |
| Codex | `AGENTS.md` (루트→cwd 체인, 기본 32 KiB 상한) | **세션 시작 시 1회 로드**. 자동 재로드는 정의되어 있지 않고, 세션 중 수정해도 반영되지 않는다 |

즉 "루트 지침 파일에 두면 살아남는다"는 Claude Code의 성질이지 보편 법칙이 아니다.
중첩 파일에 둔 규칙은 Claude Code에서도 안전하지 않다.

**좋은 CLAUDE.md는 짧다.** 시스템 프롬프트는 매 턴 전송되므로 길이가 곧 비용이다.
Claude Code in Action이 "lean CLAUDE.md"를 강조하는 이유다.

```markdown
# 나쁨 — 장황하고, 모델이 이미 아는 걸 반복
이 프로젝트는 TypeScript로 작성되었습니다. TypeScript는 정적 타입
검사를 제공하는 JavaScript의 상위집합입니다. 코드를 작성할 때는...

# 좋음 — 짧고, 이 레포에서만 참인 것
- 테스트: `npm run test` (vitest). 라이브 테스트는 `npm run test:live`
- `src/lib/ssrf-guard.ts`를 우회하는 fetch를 추가하지 말 것
- API 라우트는 `export const dynamic = 'force-dynamic'` 필요
```

**판별 기준:** "모델이 일반 지식으로 알 만한 것"은 빼고,
**"이 레포에서만 참인 것"** 만 남긴다.

### CLAUDE.md의 대안: 점진적 스펙

`CLAUDE.md` 하나가 비대해지는 문제에 대한 대응으로 나온 게
Trellis 같은 점진적 스펙 시스템이다 — 현재 단계에 관련된 표준·PRD·세션 저널만
로드한다. 사실상 **§7의 점진적 공개를 프로젝트 지침에 적용한 것**이다.

> 이 레포의 `.gitignore`는 `CLAUDE.md`와 `AGENTS.md`를 무시한다.
> 즉 각자 로컬에서 관리한다. 팀 공유가 필요하면 `docs/`에 두고 심볼릭 링크하거나,
> `.gitignore`에서 빼는 결정을 먼저 해야 한다.

### 실패 모드

- **동적 값을 앞에 둠.** 매 턴 캐시 전멸.
- **CLAUDE.md가 비대함.** 매 턴 비용 + 정작 중요한 규칙이 묻힌다.
- **모순되는 지침.** 시스템 프롬프트와 CLAUDE.md와 스킬이 서로 다른 말을 한다.
- **조립 순서가 불안정.** 섹션 순서가 실행마다 다르면 캐시가 안 걸린다.

## §11 · 에러 복구 — 긴 작업이 실패를 어떻게 견디는가

> **실패를 분류한 다음, 재시도하거나, 조정하거나, 멈춘다.**

### 분류가 먼저다

| 분류 | 예 | 처방 |
| --- | --- | --- |
| **API** | 타임아웃, 레이트 리밋, 과부하 | 백오프 재시도 |
| **툴** | 비정상 종료, 핸들러 예외 | `tool_result`로 에러를 돌려주고 모델이 판단 |
| **컨텍스트** | 프롬프트 오버플로, API가 거부하는 메시지 히스토리 | 감축 후 재시도 (§8 reactive) |
| **제어 흐름** | 같은 스텝이 반복되며 진전 없음 | 루프 감지 → 개입 또는 중단 |

**분류를 건너뛰면 전부 재시도하게 되고, 재시도로 안 고쳐지는 것에 예산을 태운다.**

### 세 갈래

1. **일시적 에러는 재시도한다.** 지수 백오프.
2. **프롬프트/출력 한도가 문제면 조정하고 재시도한다.** 감축, 모델 폴백.
3. **복구 불가면 멈춘다.** 사람에게 에스컬레이션.

3번이 가장 자주 빠진다. 무한 재시도는 복구가 아니라 예산 소각이다.

### 툴 실패는 반드시 `tool_result`로

§1에서 나온 규칙의 재등장:

```python
try:
    out = run_tool(name, args)
    err = False
except Exception as e:
    log.exception("tool %s failed", name)        # 전체 예외는 보호된 로그에만
    out = safe_message(e)                        # 모델에는 정제된 메시지만
    err = True
results.append({
    "type": "tool_result",
    "tool_use_id": block.id,                     # 원래 tool_use와 짝을 맞춘다
    "content": out,                              # is_error면 비어 있으면 안 된다
    "is_error": err,                             # API가 정의한 필드. 커스텀 필드 금지
})
```

세 가지가 다 필요하다.

- **`tool_result`를 빠뜨리면** API가 트랜스크립트를 거부하거나 모델이 무슨 일이
  일어났는지 모른다. 모든 `tool_use`에 하나씩 짝이 있어야 한다.
- **`is_error: True`를 빠뜨리면** 모델이 에러 문자열을 정상 결과로 읽고 그 위에 추론을 쌓는다.
- **`str(e)`를 그대로 넘기면** 경로, 커넥션 문자열, 토큰 조각이 컨텍스트로 샌다.
  스택트레이스는 로그로, 모델에는 **다음 행동을 알려주는 문장**을 준다 —
  `"Rate limit exceeded, retry after 30s"`이지 `"failed"`도 `str(e)`도 아니다.

마지막 항목이 §2의 툴 설계와 만나는 지점이다.

### 제어 흐름 실패 — 루프 감지

가장 다루기 어려운 종류다. 에이전트가 같은 파일을 읽고, 같은 수정을 하고,
같은 테스트를 돌리고, 다시 처음으로 가는 패턴.

LangChain이 Deep Agents를 Terminal Bench 2.0에서 30위 → 톱5로 올린 하네스 변경 중
하나가 **루프 감지 미들웨어**였다. 모델을 바꾸지 않고 얻은 결과다.

감지 신호:
- 같은 툴 + 같은 인자가 N회 반복
- 파일 상태가 M턴 동안 변하지 않음
- 토큰은 쓰는데 투두가 안 줄어듦 (**dry counter**)

### 예산은 하네스가 강제한다

```python
for attempt in range(1, budget + 1):   # 천장은 range()의 상한
    ...
```

**모델에게 "제발 멈춰"라고 부탁하는 건 힌트지 정지 조건이 아니다.**
반복 횟수, 토큰 예산, 벽시계 한도, dry counter — 무엇이든 코드가 강제해야 한다.

이 레포의 [`orchestra/dispatch.mjs`](../../orchestra/dispatch.mjs)에서
`verifyRetries`와 `timeoutMs`가 그 구현이다.

### 컨텍스트 오버플로 복구

§8의 계층적 감축을 다 돌리고도 `prompt_too_long`이 나면:

```text
reactive → head를 잘라내고 재요약, 재시도 상한 있음
```

**재시도 상한이 핵심이다.** 상한 없이 재요약하면 요약의 요약의 요약이 되어
아무 정보도 안 남은 채로 계속 돈다.

### 실패 모드

- **분류 없이 일괄 재시도.** 못 고칠 걸 반복한다.
- **재시도 상한 없음.** 예산이 조용히 소각된다.
- **툴 에러를 삼킴.** 모델이 실패를 모르고 다음 단계로 간다.
- **폴백 모델이 다른 계약을 가짐.** 툴 스키마나 thinking 블록 처리가 달라 더 깨진다.
- **에러 메시지가 사후적.** "실패했음"만 알려주면 모델이 회복할 정보가 없다.

## 이 레이어를 제거할 수 있는 조건

| 레이어 | 존재 이유 | 제거 가능 시점 |
| --- | --- | --- |
| §9 메모리 | 세션 간 상태가 없음 | 무한 컨텍스트 + 영구 세션이면. 단 **다중 세션 협업용으로는 남는다** |
| §10 캐시 경계 | 프리픽스 재전송이 비쌈 | 비용/지연이 무의미해지면 |
| §10 CLAUDE.md | 압축이 지침을 잃음 + 레포 고유 지식 | **레포 고유 지식은 영구적으로 필요** |
| §11 재시도 | API/툴이 일시적으로 실패함 | 제거 불가 (분산 시스템의 성질) |
| §11 루프 감지 | 모델이 스스로 못 빠져나옴 | 모델이 자가 감지하면. 그래도 **예산 천장은 남는다** |

§11의 예산 천장은 §3의 권한 게이트와 같은 부류다 —
**모델 능력이 아니라 당신이 감당할 비용에 대한 결정이므로 사라지지 않는다.**
