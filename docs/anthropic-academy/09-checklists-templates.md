# 09 · 체크리스트와 템플릿

바로 복사해서 쓰는 것들. 원본은 `ai-boost/awesome-harness-engineering`의
템플릿이고, 이 노트의 섹션 번호를 붙여 한국어로 옮기고 확장했다.

## 1. 하네스 리뷰 체크리스트

> 프로덕션에 올리거나 인계하기 전에 훑는다.
> **실패 항목은 블로커다.** 건너뛰는 항목은 서면 사유가 필요하다.

### 에이전트 지침 (AGENTS.md / CLAUDE.md) — §10

- [ ] 프로젝트 개요가 정확하고 최신이다
- [ ] 레포 구조가 현재 레이아웃을 반영한다
- [ ] 툴 권한이 명시적이다 — 허용 / 제한 / 금지가 모두 적혀 있다
- [ ] 검증 게이트가 정의되어 있고 명령이 실제로 동작한다
- [ ] 여러 갈래로 해석될 수 있는 지침이 없다
- [ ] **모델이 일반 지식으로 아는 내용이 들어 있지 않다** (매 턴 비용)

### 툴 설계 — §2

- [ ] 각 툴의 이름이 명확하고 모호하지 않다
- [ ] 툴 스키마가 최소다 — 에이전트가 안 쓸 optional 필드가 없다
- [ ] 에러 메시지가 **다음에 뭘 할지** 알려준다. 뭐가 잘못됐는지만 말하지 않는다
- [ ] 반환값의 형태가 일관된다 (성공/실패가 같은 shape)
- [ ] 한 툴이 하나의 개념적 일만 한다
- [ ] 위험한 툴 조합(치명적 3요소)을 검토했다

### 컨텍스트 전달 — §8

- [ ] 컨텍스트가 이 작업에 필요한 만큼으로 좁혀져 있다 — 코드베이스 전체가 아니다
- [ ] 오래 사는 상태(계획, 결정, 진행)가 프롬프트가 아니라 **파일**에 있다
- [ ] 멀티세션 작업의 압축 전략이 정의되어 있다
- [ ] 에이전트가 접근하는 컨텍스트에 비밀(자격증명, 키)이 없다
- [ ] 스텁 문자열이 매 실행마다 바이트 단위로 동일하다 (캐시)
- [ ] 캐시 경계 뒤에만 동적 값이 놓인다

### 계획 아티팩트 — §5

- [ ] 사소하지 않은 작업에 `PLAN.md`가 있다
- [ ] 각 마일스톤에 **명시적 검증 명령**이 있다
- [ ] 범위 경계(in-scope / out-of-scope)가 적혀 있다
- [ ] `IMPLEMENT.md`가 결정과 계획 이탈을 진행 중에 기록한다

### 권한과 샌드박스 — §3

- [ ] 에이전트가 작업에 필요한 **최소 권한**으로 돈다
- [ ] 파괴적 연산에 명시적 확인이 필요하다
- [ ] 네트워크 접근이 가능한 한 좁혀져 있다
- [ ] 파일시스템 접근이 프로젝트 디렉터리로 제한된다
- [ ] **샌드박스 우회 플래그가 자동화 경로에 노출되어 있지 않다**

### 검증 루프 — §21

- [ ] 에이전트 출력에 대한 테스트가 존재한다
- [ ] 에이전트가 **스스로** 검증 명령을 돌릴 수 있다 ("사람 리뷰"가 아니라)
- [ ] 검증이 PR 시점이 아니라 **작업 완료 시점에** 자동 실행된다
- [ ] 평가 기준이 작업 **시작 전에** 적혀 있다 (사후가 아니라)
- [ ] 채점자가 작업자와 **다른 컨텍스트**를 갖는다
- [ ] 재시도 예산이 코드에 하드 상한으로 존재한다

### 관측과 평가 — §20, §23

- [ ] 모든 실행이 트레이스를 남긴다
- [ ] 트레이스에 비밀이 들어가지 않는다
- [ ] 프로세스 메트릭(불법 호출, 스텝 수, 재시도)이 기록된다
- [ ] 평가 환경이 에피소드마다 리셋된다
- [ ] 같은 작업을 여러 번 돌려 노이즈와 개선을 구분한다

### 자율 실행 — §18, §21

- [ ] 성숙도 레벨(L1/L2/L3)이 명시되어 있다
- [ ] 현재 레벨에서 충분히 지루하게 정확했다는 근거가 있다
- [ ] 아무도 안 볼 때의 실패가 보고되는 경로가 있다
- [ ] 에스컬레이션 조건과 대상이 정의되어 있다

## 2. 제거 목록 — §0

> **모든 하네스 부품은 지금 모델이 못 하는 것을 메운다.**
> 그 능력이 개선되면 이 부품은 불필요해진다. 그때 지우려면 지금 적어야 한다.

| 부품 | 존재 이유 (모델이 못 하는 것) | 제거 가능 시점 | 확인 방법 |
| --- | --- | --- | --- |
| | | | |
| | | | |
| | | | |

**작성 요령:**

- "존재 이유"에 **모델의 한계**를 적어라. "편해서"는 이유가 아니다.
- "확인 방법"에 **측정 가능한 것**을 적어라 — 예: "이 부품을 끄고 eval을 돌려
  점수가 안 떨어지면"
- **권한(§3), 예산 천장(§11, §21), 관측(§20), 평가(§23)** 는 여기 들어가지 않는다.
  모델 능력이 아니라 신뢰 경계와 비용에 대한 결정이기 때문이다.

*검토일: YYYY-MM-DD · 검토자:*

## 3. `AGENTS.md` 템플릿

```markdown
# <프로젝트 이름>

<한 문단. 이게 뭐고 무엇을 위한 것인가.>

## 스택

<언어 / 프레임워크 / 런타임. 버전이 중요하면 버전까지.>

## 명령

| 목적 | 명령 |
| --- | --- |
| 개발 서버 | |
| 테스트 | |
| 린트 | |
| 빌드 | |
| 타입 체크 | |

## 레포 구조

<디렉터리별로 한 줄. 전체 트리가 아니라 의미 있는 경계만.>

## 이 레포에서만 참인 것

<모델이 일반 지식으로 알 수 없는 것들.
 관례, 함정, 우회하면 안 되는 것, 여기서만 다른 것.>

## 권한

- **허용:** <읽기, 테스트 실행, ...>
- **확인 필요:** <마이그레이션, 외부 API 호출, ...>
- **금지:** <프로덕션 배포, 시크릿 접근, ...>

## 검증 게이트

작업이 끝났다고 하기 전에 통과해야 하는 것:

1. `<명령>` — <무엇을 보장하나>
2. `<명령>` — <무엇을 보장하나>

## 하지 말 것

<구체적으로. "좋은 코드를 쓰세요"가 아니라
 "X를 우회하는 Y를 추가하지 마세요">
```

## 4. `PLAN.md` 템플릿

```markdown
# 계획: <작업 이름>

## 목표

<한 문단. 무엇이 참이 되면 이 작업이 끝난 것인가.>

## 범위

**포함:**
- <>

**제외:** ← 이 절이 없으면 에이전트가 범위를 넓힌다
- <>

## 마일스톤

### 1. <이름>

- **할 일:** <>
- **검증:** `<명령>` ← 반드시 명령. "리뷰한다"는 검증이 아니다
- **완료 조건:** <명령의 어떤 출력이 통과인가>

### 2. <이름>

- **할 일:** <>
- **검증:** `<명령>`
- **완료 조건:** <>

## 위험

| 위험 | 신호 | 대응 |
| --- | --- | --- |
| | | |

## 열린 질문

<답이 필요하지만 진행을 막지는 않는 것들.
 진행을 막는 것이면 시작하기 전에 물어라.>
```

## 5. `IMPLEMENT.md` 템플릿

```markdown
# 구현 로그: <작업 이름>

> 계획에서 벗어난 지점과 그 이유를 진행 중에 적는다.
> 사후에 쓰면 이유가 재구성되고, 재구성된 이유는 틀린다.

## 결정

### <날짜> · <한 줄 요약>

- **상황:** <무엇을 마주쳤나>
- **선택:** <무엇을 했나>
- **이유:** <왜 다른 선택지가 아니었나>
- **되돌리려면:** <이 결정이 틀렸을 때 무엇을 바꿔야 하나>

## 계획 이탈

| 계획 | 실제 | 이유 |
| --- | --- | --- |
| | | |

## 다음 세션을 위해

<컨텍스트가 초기화된 다음 실행이 알아야 할 것.
 파일 목록, 현재 단계, 마지막 검증 상태.>
```

## 6. 보드 템플릿 — 오케스트라용

```json
{
  "defaults": {
    "sandbox": "workspace-write",
    "verify": "npm run lint",
    "verifyRetries": 1,
    "timeoutMs": 1800000
  },
  "tasks": [
    {
      "id": "kebab-case-id",
      "title": "리포트에 한 줄로 나올 제목",
      "prompt": "워커를 위한 완전한 자립 브리프.\n\n워커는 이 대화를 모른다.\n- 무엇을 바꿀 것인가\n- 어떤 파일인가\n- '완료'가 무엇을 뜻하는가\n- 무엇을 건드리면 안 되는가",
      "dependsOn": [],
      "verify": "npm run test -- path/to/spec"
    }
  ]
}
```

**작성 체크:**

- [ ] `prompt`만 읽고 작업을 완수할 수 있는가? (대화 맥락 없이)
- [ ] `verify`가 이 변경을 실제로 덮는가? 너무 넓지도 좁지도 않은가?
- [ ] 두 태스크가 같은 파일을 건드리지 않는가? → 건드리면 분해를 다시
- [ ] `dependsOn`이 진짜 순서 제약인가, 아니면 불필요한 직렬화인가?
- [ ] `sandbox`가 이 작업에 필요한 최소인가?

## 7. 세션 시작 점검 — 짧은 버전

긴 세션을 시작하기 전 30초짜리 점검.

- [ ] 이 작업의 **완료 조건을 명령으로** 말할 수 있는가?
- [ ] 못 하면: 검사가 없는 작업이다. 검사를 먼저 만들 것인가, 아니면 사람이 판정할 것인가?
- [ ] 이 작업이 한 컨텍스트 윈도우에 들어가는가?
- [ ] 안 들어가면: 계획을 파일에 두는가? 세션 간 상태를 어떻게 넘기는가?
- [ ] 되돌릴 수 없는 작업이 포함되는가?
- [ ] 포함되면: 그 지점에 승인 게이트가 있는가?
- [ ] 실패했을 때 그걸 어떻게 알게 되는가?
