# Orchestra — Claude Code 지휘, Codex 연주

> **Claude Code가 주체(지휘자)이고, `codex exec` 세션들이 동시에 연주한다.**
> 한 태스크 = 한 git worktree = 한 비대화형 Codex 세션.

이 디렉터리는 [`docs/anthropic-academy`](../docs/anthropic-academy/) 학습 노트의
§12(태스크 시스템), §13(백그라운드 실행), §15(워크트리 격리), §21(루프 엔지니어링)을
실제로 돌아가는 코드로 구현한 것이다. 노트가 이론이면 여기가 실습이다.

---

## 구조

```
              ┌──────────────────────────────┐
              │  Claude Code  (지휘자)        │
              │  /orchestra 슬래시 커맨드     │
              │  · 분해   · 병합   · 판단     │
              └───────────────┬──────────────┘
                              │ board.json 작성
                              ▼
              ┌──────────────────────────────┐
              │  orchestra/dispatch.mjs      │
              │  · 의존성 해석 (§12)          │
              │  · 동시성 풀   (§13)          │
              │  · 워크트리    (§15)          │
              │  · 검증 루프   (§21)          │
              └───┬──────────┬──────────┬────┘
                  │          │          │   동시 실행
        ┌─────────▼──┐ ┌─────▼──────┐ ┌─▼──────────┐
        │ codex exec │ │ codex exec │ │ codex exec │
        │ worktree A │ │ worktree B │ │ worktree C │
        │ branch     │ │ branch     │ │ branch     │
        │ orchestra/a│ │ orchestra/b│ │ orchestra/c│
        └─────┬──────┘ └─────┬──────┘ └─────┬──────┘
              │ verify       │ verify       │ verify
              ▼              ▼              ▼
              └──────────► .orchestra/report.md ──► 지휘자가 검토·병합
```

**분업의 근거:** 지휘자는 판단이 필요한 부분(무엇을 어떻게 쪼갤지, 무엇을 병합할지)을
갖고, 하네스는 판단이 필요 없는 부분(격리, 동시성, 타임아웃, 검증)을 갖는다.
이게 §0의 "모델이 판단을 소유하고 하네스가 환경을 소유한다"의 구체형이다.

## 사전 준비

| 필요 | 확인 |
| --- | --- |
| Node.js 18+ | `node --version` |
| git 2.20+ (worktree) | `git worktree list` |
| Codex CLI | `codex --version` — 없으면 `--dry-run`만 동작 |
| Codex 인증 | `codex login` 또는 환경변수 |

리포지토리가 git 레포여야 한다. 워크트리를 쓰기 때문이다.

## 사용법

### 1. 태스크 보드 작성

`orchestra/board.json`:

```json
{
  "defaults": {
    "sandbox": "workspace-write",
    "verify": "npm run lint",
    "verifyRetries": 1,
    "timeoutMs": 1800000
  },
  "tasks": [
    {
      "id": "schema",
      "title": "Add the alert severity schema",
      "prompt": "전체 브리프를 여기에. 워커는 이 대화를 모른다.",
      "dependsOn": [],
      "verify": "npm run test -- src/lib/schema"
    },
    {
      "id": "api",
      "title": "Wire the schema into /api/alerts",
      "prompt": "...",
      "dependsOn": ["schema"],
      "verify": "npm run test -- src/app/api/alerts"
    }
  ]
}
```

| 필드 | 의미 |
| --- | --- |
| `id` | kebab-case. 브랜치 `orchestra/<id>`, 워크트리 `.orchestra/worktrees/<id>`가 된다 |
| `prompt` | **자립적이어야 한다.** 워커는 빈 컨텍스트로 시작한다 |
| `dependsOn` | 앞 태스크의 산출물이 입력일 때만. 병렬 가능한 걸 직렬화하지 말 것 |
| `verify` | 종료 코드로 통과/실패를 판정하는 명령. **없으면 검증 없이 통과 처리된다** |
| `verifyRetries` | 검증 실패 시 재시도 횟수. 실패 출력이 다음 프롬프트에 실려 들어간다 |
| `sandbox` | Codex 샌드박스 정책. 기본 `workspace-write` |
| `timeoutMs` | 세션당 벽시계 한도. 초과 시 SIGKILL |

### 2. 드라이런 — 항상 먼저

```bash
node orchestra/dispatch.mjs --dry-run
```

실행될 `codex exec` 명령을 그대로 출력한다. 디스크에 아무것도 쓰지 않는다.

### 3. 실행

```bash
node orchestra/dispatch.mjs -j 3
```

| 플래그 | 의미 |
| --- | --- |
| `-j, --concurrency N` | 동시 Codex 세션 수 (기본 3) |
| `--only a,b` | 일부만 실행. 의존 태스크는 자동으로 끌어온다 |
| `--base <ref>` | 워크트리를 이 ref에서 분기 (기본 현재 HEAD) |
| `--fresh` | 이전 상태 무시하고 통과한 태스크도 재실행 |
| `--keep-worktrees` | 깨끗한 워크트리도 남긴다 |
| `--board <file>` | 다른 보드 파일 |

### 4. Claude Code에서 지휘

```
/orchestra 알림 심각도 스키마를 만들고 API와 UI에 연결해줘
```

슬래시 커맨드가 분해 → 보드 작성 → 드라이런 → 백그라운드 실행 → 수집·병합의
4단계를 이끈다. 개별 워커 결과 감사는 `codex-liaison` 서브에이전트가 맡는다.

## 산출물

```
.orchestra/
├── state.json              태스크별 최종 상태 (재개 가능) — §12
├── report.md               통과/실패 표 + 태스크별 상세
├── worktrees/<id>/         워커의 격리된 체크아웃 — §15
└── runs/<id>/
    ├── events.jsonl        codex --json 이벤트 스트림 (전체 트레이스) — §20
    ├── last.md             워커의 최종 메시지 (주장이지 증거가 아님)
    └── stderr.log
```

`.orchestra/`는 `.gitignore`에 들어 있다. **워커의 작업물은 브랜치에 커밋되고,
런타임 산출물만 무시된다.**

## 설계 결정과 그 이유

### 왜 워크트리인가 (§15)

같은 디렉터리에서 두 에이전트를 돌리면 서로의 편집을 덮어쓴다. 워크트리는
같은 `.git`을 공유하면서 **작업 디렉터리만 분리**한다. 그래서 브랜치는 즉시
공유되고 파일 충돌은 병합 시점까지 미뤄진다.

정리 규칙: **깨끗한 워크트리는 지우고, 더러운 워크트리는 남긴다.**
커밋되지 않은 작업물을 조용히 버리지 않기 위해서다.

### 왜 검증이 하네스에 있는가 (§21)

워커가 "다 됐습니다"라고 말하는 건 주장이다. 이 하네스에서 통과의 정의는
**`verify` 명령의 종료 코드가 0인 것**이고, 그 판정은 모델이 말을 얹을 수 없는
곳(부모 프로세스)에서 일어난다.

실패 시 재시도 프롬프트에 **실패 출력이 데이터로 실려 들어간다** — 두 번째
시도는 첫 번째가 무엇을 틀렸는지 안다. 예산(`verifyRetries`)은 `for` 루프의
상한이라 모델이 말로 넘어설 수 없다.

### 왜 샌드박스 우회 플래그가 없는가 (§3)

`codex exec`에는 `--dangerously-bypass-approvals-and-sandbox`가 있지만
이 디스패처는 **그 플래그를 노출하지 않는다.** 태스크가 더 넓은 권한이 필요하면
보드에서 `sandbox`를 명시적으로 넓히는 게 맞고, 그건 사람이 내리는 결정이다.
권한은 모델이 좋아진다고 없어지는 레이어가 아니다 — 감당할 수 있는 피해 범위에
대한 결정이다.

### 보드는 코드다 — 신뢰 경계

`verify`는 **설계상 셸 명령줄**이다. 실제 검사는 파이프와 `&&`가 필요하다:

```
npm run lint && npm run test -- src/lib
```

따라서 `board.json`은 `package.json`의 `scripts`, Makefile, 그리고 `dispatch.mjs`
자체와 **같은 신뢰 수준**에 있다. 그걸 쓸 수 있는 사람은 이미 여기서 코드를 돌릴 수 있다.
**보드 변경은 스크립트 변경처럼 PR에서 리뷰하라.**

> 공백으로 쪼개고 `shell`을 끄는 건 이 경계를 옮기지 않는다 — `sh -c '...'`가 그대로
> 통과한다. 반면 모든 복합 명령을 **조용히 잘못 실행한다**: `echo A && echo B`가
> `echo "A && echo B"`가 되어 엉뚱한 걸 검사하고 통과로 보고한다.
> 그래서 그렇게 하지 않는다.

대신 지켜야 할 것:

- **레포 밖 보드를 실행하지 마라.** 남이 건네준 보드 파일은 리뷰받지 않은 코드다.
  `--board`가 레포 밖을 가리키면 디스패처가 경고한다.
- **`--dry-run`을 먼저 돌려라.** 실행될 `codex exec` 명령과 `verify` 명령이 그대로 출력된다.
- **`prompt`도 마찬가지다.** 워커에게 뭘 시키느냐가 `verify`만큼 중요하다.

### 실패한 태스크도 커밋한다

`passed`든 `failed`든 워크트리가 더러우면 커밋한다. 실패한 시도가 남긴 절반의
작업물이 다음 판단에 유용한 경우가 많고, 조용히 버리면 그걸 잃는다.

## 실패 모드

| 증상 | 원인 | 대응 |
| --- | --- | --- |
| `codex CLI not found on PATH` | Codex 미설치 | 설치하거나 `--dry-run` |
| 모든 태스크가 `blocked` | 의존 태스크가 실패 | 리포트에서 최초 실패 지점부터 |
| 병합 충돌이 반복됨 | 분해를 잘못한 것 | 파일/모듈 경계로 다시 쪼갠다 |
| 검증은 통과했는데 결과가 틀림 | `verify`가 변경 범위를 안 덮음 | 검사를 좁고 정확하게 |
| 워커가 테스트를 지워서 통과 | 검증만으로는 못 막음 | `codex-liaison` 감사 + diff 리뷰 필수 |
| 워크트리가 남아 있음 | 커밋 안 된 변경이 있었음 | 의도된 동작. 확인 후 수동 정리 |

마지막에서 두 번째 행이 중요하다. **검증 루프는 바닥이지 천장이 아니다.**
"체크를 통과시키기 위해 체크를 약화시키는" 실패는 종료 코드로 잡히지 않는다.
그래서 `codex-liaison`이 diff를 보고, 사람이 최종 병합을 승인한다.

## 이 레이어를 제거할 수 있는 조건

| 부품 | 존재 이유 | 제거 가능 시점 |
| --- | --- | --- |
| 워크트리 격리 | 병렬 에이전트가 서로를 덮어씀 | 에이전트 런타임이 격리를 기본 제공하면 |
| 검증 루프 | 모델의 "완료" 선언이 신뢰 불가 | 신뢰 가능해져도 — 회귀 방지용으로 남는다 |
| 재시도 예산 | 무한 루프 방지 | 제거 불가 (하네스가 강제하는 천장) |
| 의존성 해석 | 순서가 필요한 작업이 있음 | 모델이 직접 스케줄링해도 되는 규모면 |
| 샌드박스 정책 | 신뢰 경계 | **제거 불가** |
